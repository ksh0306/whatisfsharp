# 15챕터 용어 후보 (F# 전문가 검수, 후보 모드)

`docs/ko/GLOSSARY.md` 는 읽기만 했고 편집하지 않았다(13·14챕터 전문가와 동시 작업 중).
아래 행을 알파벳 순 위치에 삽입하면 된다. `[기확정 변경 제안]` 은 없다.

13·14챕터와 겹치는 항목이 있다. 겹치는 행은 표 아래 3절에 따로 모았다.
병합자는 세 후보 파일을 나란히 놓고 하나로 정하고, 갈리면 이 파일의 근거를 함께 보라.

## 1. 확정 제안 (그대로 삽입)

| 영어 | 한국어 표기 | 비고 |
|---|---|---|
| attribute function | 특성 함수 | View Engine 에서 HTML 특성 하나를 만드는 함수. 이름 앞에 밑줄이 붙는다(`_class`·`_href`·`_datetime`). 기확정 `attribute`→특성 을 그대로 이어 쓴 것이고 `[<Fact>]` 류의 F# 특성과 영어 낱말이 겹치므로, 두 개념이 한 단락에 오는 자리에서는 "HTML 특성" 으로 갈라 쓴다. "속성 함수" 쓰지 않는다(`property`→프로퍼티 와 충돌한다). 13챕터가 이미 이 표기를 쓴다. 13·15챕터 본론 |
| character reference | 문자 참조 | `&lt;`·`&amp;`·`&#39;` 처럼 HTML 에서 문자를 대신하는 표기. HTML 명세 용어 character reference 를 옮긴 것이다. 통용 표기는 "HTML 엔티티" 쪽이 흔하나, 엔티티는 이름 있는 참조(`&amp;`)만 가리키고 숫자 참조(`&#39;`)를 포함하지 않는다. 15챕터가 실측한 출력에 숫자 참조가 나오므로 둘을 함께 덮는 "문자 참조" 를 택한다. 비고에 "엔티티라 부르는 문헌도 있다" 를 남겨 둔다. 15챕터 본론 |
| content root | 콘텐츠 루트 | 앱이 자기 파일을 찾는 기준 폴더. 프로젝트 폴더가 기본이고 웹 루트(`wwwroot/`)가 그 아래에 놓인다. MS ko 표기와 일치. "내용 루트" 쓰지 않는다. 15챕터 |
| element function | 요소 함수 | View Engine 에서 HTML 요소 하나를 만드는 함수(`html`·`p`·`li`). 결과 타입이 모두 `XmlNode` 라서 조각을 함수로 뺄 수 있다. 요소 대부분이 특성 목록과 자식 목록 둘을 받고, `meta`·`link` 처럼 자식을 담을 수 없는 요소는 특성 목록만 받는다(자식 목록을 붙이면 오류 FS0003 — 실측). "태그 함수" 쓰지 않는다. 13챕터가 이미 이 표기를 쓴다. 13·15챕터 본론 |
| escape | 이스케이프 | HTML 문법에 쓰이는 문자를 문자 참조로 바꾸는 것. 정착된 음차를 쓰고 "탈출"·"회피" 로 옮기지 않는다. 동사형은 "이스케이프한다". View Engine 의 `str` 과 특성 함수가 `<`·`>`·`&`·`"`·`'` 를 바꾸고 `rawText` 는 바꾸지 않는다(실측). 15챕터 본론 |
| master page | 마스터 페이지 | 원서 절 제목 Adding a Master Page(원서 p.186)의 표기. 여러 화면이 공유하는 껍데기를 가리키는 ASP.NET 계열 이름이고 MS ko 도 "마스터 페이지" 다. Giraffe 에서 이 역할을 하는 것은 상속도 특별한 규칙도 없는 평범한 함수이므로, 노트 본문은 그 함수를 "공용 레이아웃" 이라 부르고 첫 등장에서 "다른 뷰 엔진에서 마스터 페이지나 레이아웃이라 부르는 것" 으로 잇는다(15챕터가 그렇게 적었다). 절 제목의 원서 영문은 남긴다. F# 코드를 설명하는 자리에서 "마스터 페이지" 를 쓰지 않는다. 15챕터 본론 |
| partial view | 부분 뷰 | 화면 조각을 만드는 함수. 원서 p.190 표기 partial view 를 옮긴 것이고 실체는 `Inspection -> XmlNode` 같은 함수다. 13챕터 노트가 이미 이 표기를 예고해 두었다. "파셜 뷰"·"부분 화면" 쓰지 않는다. 13·15챕터 |
| `rawText` | `rawText` | 함수 이름은 번역하지 않는다. 문자열을 이스케이프하지 않고 그대로 끼워 넣는다. 이미 HTML 인 조각에만 쓰고 바깥에서 들어온 값에는 쓰지 않는다는 규칙을 함께 못박는다. 짝이 되는 `str` 은 이스케이프한다. 15챕터 본론 |
| static files | 정적 파일 | 서버가 내용을 손대지 않고 그대로 내보내는 파일(CSS·JavaScript·이미지·글꼴). MS ko 표기와 일치. "스태틱 파일" 쓰지 않는다. 15챕터 본론 |
| static file middleware | 정적 파일 미들웨어 | `UseStaticFiles()` 가 파이프라인에 넣는 미들웨어. 확장자와 `Content-Type` 대응 표를 들고 있고 표에 없는 확장자는 내보내지 않는다(실측: `.xyz` 는 404). 라우팅이 아니라 미들웨어가 처리하므로 정적 파일 경로는 엔드포인트 목록에 적지 않는다. 기확정 계열이 될 `middleware`→미들웨어(13챕터)를 그대로 이어 쓴다. 15챕터 본론 |
| web root | 웹 루트 | 정적 파일을 내보내는 기준 폴더. 기본값은 콘텐츠 루트 아래 `wwwroot/` 이고 폴더 이름은 번역하지 않고 `wwwroot/` 로 적는다. 바꾸려면 `WebApplication.CreateBuilder(WebApplicationOptions(WebRootPath = ...))` 로 넘긴다(실측 — `builder.WebHost.UseWebRoot` 는 이 호스팅 모델에서 `NotSupportedException` 이다). MS ko 표기와 일치. 15챕터 |

## 2. 기확정 표기 확인 (표에 넣지 않음)

15챕터가 쓰는 기확정 용어는 표기를 그대로 따르고 있다. 변경 제안 없다.

- `list comprehension`→리스트 컴프리헨션, `implicit yield`→암시적 yield: 부분 뷰를 늘어놓는
  `[ ... for x in xs do ... ]` 설명이 두 표기를 그대로 쓴다. 줄임형 "컴프리헨션" 도 기확정 규칙대로다.
- `Domain-Specific Language (DSL)`→도메인 특화 언어: 13챕터에서 병기를 마쳤고 15챕터는
  "View Engine DSL" 로만 쓴다. 규칙에 맞는다.
- `attribute`→특성, `discriminated union`→판별 유니온, `single-case discriminated union`,
  `type annotation`→타입 주석, `signature`→시그니처, `unwrap`→벗기다: 전부 기확정 표기와 일치.
- `parameter`→매개변수 / `argument`→인자: 한 곳이 어긋난다(검수 보고서 `개선 권장` 참조).
  용어집이 아니라 노트를 고칠 일이다.

## 3. 13·14챕터와 겹쳐 병합자가 정할 항목

세 챕터가 같은 낱말을 쓰므로 표기가 갈릴 수 있다. 15챕터가 쓴 표기와 근거만 적는다.
13·14챕터 후보 파일이 다른 표기를 올리면 그쪽 근거와 견주어 하나로 정하라.

| 영어 | 15챕터가 쓴 표기 | 15챕터의 근거 |
|---|---|---|
| middleware | 미들웨어 | 13챕터가 먼저 쓴 표기를 그대로 따랐다. 15챕터는 `UseStaticFiles` 한 줄을 더하는 자리와 순서 실험에서 이 낱말을 쓴다 |
| View Engine | View Engine | 제품 이름의 일부라 번역하지 않았다. 첫 등장은 "Giraffe View Engine", 이후 "View Engine". "뷰 엔진" 은 다른 엔진 일반을 가리키는 자리에만 썼다(마스터 페이지 설명) |
| `htmlView` | `htmlView` | 핸들러 이름은 번역하지 않는다. `XmlNode -> HttpHandler`. `text`·`json`·`negotiate` 와 같은 계열이므로 13·14챕터의 처리에 맞춘다 |
| routing / endpoint / handler | 라우팅 / 엔드포인트 / 핸들러 | 13·14챕터 표기를 그대로 따랐다. 15챕터가 새로 정한 것은 없다 |
| dependency injection / singleton | 의존성 주입 / 싱글턴 | 14챕터 표기를 그대로 따랐다 |
| content negotiation | 내용 협상 | 14챕터 표기를 그대로 따랐다. 15챕터는 화면과 API 를 경로로 가르는 이유를 적을 때 한 번 쓴다 |

웹 맥락의 `pipeline` 은 15챕터가 쓰지 않았다. 미들웨어 순서를 말할 때 "요청이 지나는 길" 로 풀었다.
기확정 `pipeline`→파이프라인 은 `|>` 로 값을 흘려보낸 코드 형태를 가리키는 행이므로(용어집 211행),
웹 맥락에 같은 낱말을 쓰면 한 표기가 두 개념을 가리키게 된다. 13·14챕터도 풀어 쓰는 쪽이면
새 행을 만들 필요가 없다. 어느 챕터가 이 낱말을 꼭 써야 한다면
`middleware pipeline`→미들웨어 파이프라인 처럼 한정어를 붙인 별도 행으로 올려야 한다.
