### 3. `>=>` 를 함수 합성 연산자로 읽히게 하는 자리 (전문가 미지적)
용어집 `compose operator (>=>)` 행은 `>=>` 에 한국어 이름을 붙이지 않고 `>>`(함수 합성 연산자)와
갈라 쓰라고 못박는다. 전문가가 344줄을 "`>>` 와는 잇는 방식이 다르다" 로 바꾸면 287줄만 옛 그림으로 남는다.
- [13:287] 현재: `이것이 2챕터에서 본 함수 합성이 웹 코드에 나타난 모습이고, Giraffe 는 그 합성을 `>=>` 연산자로 준다.`
  수정: `이것이 2챕터에서 본 함수 합성과 같은 발상이 웹 코드에 나타난 모습이고, Giraffe 는 핸들러를 이어 붙이는 `>=>` 를 준다.`
  (찾을 문자열: `Giraffe 는 그 합성을` — 1회)

## 선행 검수 지시서의 문제

전문가 교체문·병합 교체문에서 용어집 위반, 문법 문제, 중복 서술을 찾은 것이다. 아래 문면을 쓰라.

### 1. 전문가 항목 1 (161줄 해석기) — "처리기" 는 금지 표기이고, 새 112줄 불릿과 한 문장이 겹친다
문제 셋. (가) "다음 처리기로 넘어간다" 의 "처리기" 는 용어집 `handler` 행이 금지한 표기다.
(나) "그래서 `#r` 에는 코드가 타입 이름을 직접 적는 어셈블리만 적으면 되고 나머지는 실행 중에 해석기가 채운다" 는
전문가가 112줄에 새로 더하는 불릿과 같은 말이다(50줄 거리에서 두 번 나온다). 112줄 쪽에 두고 여기서 뺀다.
(다) "그것이 모두 그 폴더에만 있다" 의 "그것" 이 복수 선행어를 받고, "실행 중에" 가 한 불릿에 세 번 나온다.

교체문(이것을 쓰라):
```
- (2)의 해석기가 없으면 실행 중에 `FileNotFoundException` 이 난다. FSI 의 기본 로드 컨텍스트(`AssemblyLoadContext.Default`)는 런타임 폴더와 명시적으로 준 어셈블리 쪽만 뒤지고 ASP.NET Core 공유 프레임워크 폴더는 뒤지지 않는다. `#r` 로 적은 10개가 다시 끌어오는 어셈블리는 50개가 넘는데(Kestrel, Configuration, Options, Primitives 같은 것들) 그 어셈블리가 모두 그 폴더에만 있다. 이름만 보고 그 폴더에서 찾아 주면 해결된다. 해석기가 `null` 을 돌려주는 것은 "나는 모른다"는 뜻이고, 그러면 로더가 다음 방법을 시도한다 — `Giraffe` 처럼 NuGet 캐시에서 오는 어셈블리는 그 경로로 해결된다.
```
전문가가 112줄에 더하는 불릿은 그대로 쓴다. 두 불릿이 겹치지 않게 짝을 맞춘 것이다.

### 2. 전문가 항목 2 / 병합 4.1 (버전 선택 코드) — `failwithf` 문면의 조사가 틀렸다
`%s` 에 들어가는 값은 `.../shared/Microsoft.AspNetCore.App` 이므로 "App 가 없다" 가 된다. 조사가 값에 붙지 않게 바꾼다.

코드의 나머지 줄과 주석 `// 폴더 이름을 문자열로 비교하면 10.0.9 가 10.0.11 보다 크므로 Version 으로 비교한다` 는 그대로 쓴다.
`printfn` 이 아니므로 열 정렬에 영향이 없다.

### 3. 전문가 항목 3 / 병합 4.2 (끊긴 링크 검사) — 조사가 값에 붙는다

### 4. 전문가 항목 4 (303줄 `RequestErrors.notFound`) — "감싼 핸들러" 가 어느 쪽인지 흐리다
"그다음에 감싼 핸들러가 돌아간다" 는 감싸는 쪽으로도 읽힌다. "돌아간다" 도 "반환한다" 로 읽힐 수 있다.
교체문(이것을 쓰라):
```
- 파이프 두 개로 읽으면 뜻이 그대로 드러난다. 문자열을 본문으로 쓰는 핸들러를 만들고, 그것을 404 로 감싼다. `RequestErrors.notFound h` 의 실체는 `setStatusCode 404 >=> h` 다. 상태 코드를 404 로 먼저 정하고 그다음에 안쪽 핸들러가 실행된다. `text` 는 본문과 `Content-Type` 만 건드리고 상태 코드를 건드리지 않으므로 404 가 그대로 남는다. 200 을 나중에 404 로 덮는 것이 아니다 — `>=>` 는 왼쪽이 먼저다.
```
함께: 위 "용어 일관성 10" 의 293줄 수정을 같이 적용하라. 293 을 두면 바로 위에서 "404 로 바꿔 감싼다" 고 말한 뒤
303 에서 "덮는 것이 아니다" 라고 뒤집는 모양이 된다.

### 5. 전문가 항목 5 (39줄 `Func<string>`) — 주술 불일치와 오류 문장의 어순
"`MapGet` 은 ... 오버로드다" 는 메서드를 오버로드와 같은 것으로 놓는다. `MapGet` 은 오버로드가 여럿 있는 메서드다.
"`error FS0001` 로 `HttpContext` 를 요구한다" 도 주체가 뒤바뀌어 있다.
교체문(이것을 쓰라):
```
- `MapGet` 에는 C# 을 염두에 두고 만든 오버로드가 여럿 있다. 하나는 `RequestDelegate` 를 받고 다른 하나는 `System.Delegate` 를 받는다. F# 은 대상 델리게이트(delegate) 타입이 정해진 자리라면 람다를 자동으로 변환해 주지만, `fun () -> "Hello World!"` 를 그냥 넘기면 `RequestDelegate` 오버로드가 잡혀 `HttpContext` 를 요구하는 `error FS0001` 이 난다. `System.Delegate` 쪽은 어느 델리게이트를 만들지 정할 수 없다. 그래서 `Func<string>(...)` 으로 이름을 대 준다. 이 어색함이 Giraffe 를 쓰는 이유 중 하나다.
```

### 6. 전문가 항목 6 (3줄 서두) — 접속이 끊긴 문장과 병기 누락
"하나하나는 작고, 나머지는 ... 장면이다" 는 앞뒤 절의 서술어가 맞물리지 않는다. 익명 레코드 병기도 빠졌다
(이 수정으로 첫 등장이 3줄로 옮겨지므로 308줄의 병기는 떼야 한다 — "용어 일관성 4" 참고).
교체문(불릿이 아니라 3줄 인용 문단의 가운데 부분이다. 앞의 "여기서부터 ... 함수로 적는다." 와
뒤의 "이 챕터에서 세운 프로젝트를 ..." 은 그대로 둔다):
```
새 문법이 몇 개 나온다. 프로퍼티를 설정할 때 쓰는 할당 연산자 `<-` 와 그 짝인 `mutable`, 값을 그 자리에서 만드는 익명 레코드(anonymous record) `{| ... |}`, 핸들러를 이어 붙이는 `>=>`, 비동기 작업을 적는 `task` 계산 식(computation expression)이다. 하나하나는 작다. 나머지는 2챕터의 함수 합성, 3챕터의 `Option`·`Result`, 9챕터의 단일 케이스 판별 유니온, 4챕터의 파일 컴파일 순서가 그대로 쓰이는 장면이다.
```

### 7. 전문가 항목 7 (162줄 `#load`) — "방법도 되지만" 은 비문이고, 4.2 코드 검사의 짝 산문이 없다
병합 4.2 가 코드에 원본 존재 검사를 넣는데 그것을 설명하는 산문이 어디에도 없다(병합 4.3 은 4.1 의 짝만 다룬다).


### 8. 전문가 개선 권장 [13:273-276] (타입 약어 블록) — 주석의 이름 순서가 정의 순서와 다르다
주석은 `HttpFunc·HttpFuncResult·HttpHandler` 인데 정의는 `HttpFuncResult`→`HttpFunc`→`HttpHandler` 순이다.
블록 전체를 이것으로 바꾼다.
```fsharp id=13-server
// HttpFuncResult·HttpFunc·HttpHandler 가 무엇의 약어인지 컴파일러로 확인한다
// 타입 약어는 원래 타입과 같은 것이므로, 아래 세 정의가 컴파일된다는 것이 곧 약어가 그 모양이라는 뜻이다
let asHttpFuncResult (t: Threading.Tasks.Task<HttpContext option>) : HttpFuncResult = t
let asHttpFunc (f: HttpContext -> HttpFuncResult) : HttpFunc = f
let asHttpHandler (h: HttpFunc -> HttpContext -> HttpFuncResult) : HttpHandler = h
printfn "세 약어를 컴파일러가 받아들였다"
```
`printfn` 이 라벨 없는 한 문장이므로 열 정렬 문제는 없다. 269줄("컴파일러에게 물어보면 이렇게 확인된다"),
279줄("정리하면 세 줄이다"), 361줄("앞 절의 세 줄을 확인하는 셈이다")은 그대로 맞는다.

### 9. 전문가 개선 권장 [13:344] (`>=>` 와 `>>` 대비) — 2챕터 참조가 사라지고 "기대고 있다" 가 문체와 다르다
420줄이 "이 성질에 기댄다" 로 적는다. 진행형을 쓰지 않는다. 3줄 서두가 "2챕터의 함수 합성" 을 예고하므로 참조를 남긴다.
교체문(첫 불릿만. 둘째 불릿 "이어 붙인 결과의 타입도 ..." 는 전문가안 그대로):
```
- `>=>` 가 핸들러 두 개를 이어 붙인다. 왼쪽 핸들러가 응답 헤더를 하나 달고 다음 핸들러를 부르며, 오른쪽 핸들러가 본문을 쓴다. 2챕터에서 본 `>>` 와는 잇는 방식이 다르다. `>>` 는 앞 함수의 결과를 뒤 함수의 입력으로 넘기지만, `>=>` 는 오른쪽 핸들러를 왼쪽 핸들러의 `next` 자리로 넣는다. 그래서 왼쪽이 `next` 를 부르지 않으면 오른쪽은 아예 실행되지 않는다. 상태 코드를 먼저 정하고 본문을 나중에 쓰는 `RequestErrors.notFound` 가 이 순서에 기댄다.
```

### 10. 전문가 개선 권장 [13:258-259] (이전 방식) — "처리한 것이 나오면" 이 걸린다
교체문(이것을 쓰라):
```

```

   "13챕터와 같다" 는 문장이 거짓이 된다. 14챕터도 같이 넓혀야 한다.
3. [15:666], [15:691] "요청이 지나는 길" 이 두 곳 남아 있다. 병합 보고서 5.1 은 15챕터 전문가가 이 표현을 없앤다고 적었으나
   현재 파일에는 두 곳이 그대로다. 13챕터가 미들웨어 파이프라인이라는 이름을 붙인 뒤이므로 691줄(인수인계 문단)은

4. 준비 코드(병합 4.1·4.2)는 세 챕터를 함께 고쳐야 한다. 13챕터에만 있는 짝 주석·산문(병합 4.3)에

## `printfn` 열 정렬 확인 (요청 항목)

- 이 지시서와 전문가·병합 지시서가 바꾸는 `printfn` 은 276줄 하나뿐이고 라벨 없는 한 문장이므로 정렬 영향이 없다.
- 607줄 `printfn "%-18s %d  %s"` 와 613-625줄의 기대 출력은 어느 지시서도 건드리지 않는다. 폭 18 을 그대로 두라.
- 157줄 `printfn "ASP.NET Core %s"` 도 그대로다(병합 보고서가 고친 코드에서도 `ASP.NET Core 10.0.11` 이 나온다고 실측 보고했다).
- 병합 2·3번의 `failwithf` 문면 수정은 서식 문자열 하나짜리 오류 메시지라 정렬과 무관하다.
