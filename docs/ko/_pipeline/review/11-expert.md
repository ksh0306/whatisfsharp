## 수정 필요 (기술 오류)

- [11-recursion.md:64] `인자를 (-1) 로 괄호에 넣은 것은 orderCount -1 이 뺄셈으로 읽히기 때문이다`
  — 틀렸다. F# 은 앞에 공백이 있고 뒤에 공백이 없는 `-` 를 인접 접두 마이너스로 읽는다.
  실측하면 `orderCount -1` 은 `orderCount (-1)` 과 똑같이 파싱돼 그대로 실행되고(스택을 넘긴다),
  값에 붙이면 적용으로 읽힌 것이 드러난다 — `let g = 10` 뒤의 `g -1` 은 오류 FS0003
  `이 값은 함수가 아니며 적용할 수 없습니다.` 가 난다. 뺄셈으로 읽히는 것은 `-` 양쪽에
  공백을 둘 때다(`orderCount - 1` → 오류 FS0001). 또 `f -m` 처럼 이름에도 접두 마이너스가 붙는다.
  교체 문장:
  `F# 은 앞에 공백이 있고 뒤에 공백이 없는 -1 을 음수 리터럴로 읽으므로 orderCount -1 도 똑같이 동작한다. 뺄셈으로 읽히는 것은 orderCount - 1 처럼 - 양쪽에 공백을 둘 때이고 그때는 오류 FS0001 이 난다. 괄호는 그 혼동을 없애는 관례다.`

- [11-recursion.md:316] `나누는 술어가 <= 인 것도 이유가 있다. 같은 값이 여러 개일 때 그 값들이
  한쪽으로 모여야 원소 수가 유지된다.` — 틀렸다. `rest` 의 모든 원소가 두 쪽 중 정확히 한 쪽에
  들어가므로 술어를 무엇으로 두든 원소 수는 유지된다. `<` 로 바꿔 실측하면 결과가 `<=` 판과
  같고(`[3; 7; 7; 12; 12; 41; 41; 55; 88; 130]`), 같은 값만 5개인 입력과 무작위 5000개
  입력에서도 `List.sort` 와 일치했다. 지금 문장은 "`<` 로 적으면 원소가 사라진다"는 오해를 만든다.
  교체 문장(앞 문장인 기준값 설명은 정확하므로 그대로 두고 이 두 문장만 바꾼다):
  `술어를 <= 로 둘지 < 로 둘지는 결과를 바꾸지 않는다. 기준값과 같은 값이 앞쪽 묶음으로 가느냐 뒤쪽으로 가느냐만 달라지고, 어느 쪽이든 원소는 두 묶음 중 정확히 한 곳에 들어가므로 개수와 정렬 결과가 같다.`

- [11-recursion.md:93] `두 함수 모두 재귀 호출의 결과가 곧 자기 결과이므로 프레임이 쌓이지 않고,
  그래서 10만 일도 문제없이 돈다.` — 두 가지 문제가 있다.
  (1) 근거가 되지 못한다. 같은 노트 157줄이 소박한 재귀도 20만까지 통과했다고 적었으므로
      10만은 꼬리 호출의 증거가 아니다. 블록의 인자를 10만에서 1000만으로 올려야 증거가 된다.
      실측: `dotnet fsi` 에서 `dayShiftOn 10_000_000` 과 `dayShiftOn 100_000_000` 모두 통과하고
      단위 전체 실행 시간은 2.7초로 지금과 같다.
  (2) 조건이 빠졌다. 자기 자신을 직접 부르는 꼬리 호출은 컴파일러가 반복문으로 바꾸므로 항상
      성립하지만, 상호 재귀처럼 다른 함수로 가는 꼬리 호출은 `--tailcalls+` 일 때만 성립한다.
      실측: 같은 코드를 프로젝트에 넣어 `dotnet run -c Debug`(fsc 인자에 `--tailcalls-`)로 돌리면
      자기 재귀판 `sumLoop 10_000_000` 은 통과하는데 `dayShiftOn 10_000_000` 은
      `Stack overflow.` / `Repeated 130850 times:` 로 죽는다.
      `-c Release`, 또는 `-c Debug -p:Tailcalls=true` 로 전체 재빌드하면 통과한다
      (증분 빌드로는 옵션이 반영되지 않는다).
      노트는 `[<TailCall>]` 절에서 이미 FSI 와 프로젝트 빌드를 갈라 적었으니 여기도 같은 정밀도가 필요하다.
  블록 수정: 마지막 `printfn` 을
  `printfn "10000000일 뒤 주간조 근무? %b" (dayShiftOn 10_000_000)   // 10000000일 뒤 주간조 근무? true`
  로 바꾼다(실측 출력 확인).
  교체 문장:
  `두 함수 모두 재귀 호출의 결과가 곧 자기 결과이므로 프레임이 쌓이지 않는다. 그래서 1000만 일도 즉시 끝난다. 다만 이 최적화는 조건이 하나 붙는다. 자기 자신을 직접 부르는 꼬리 호출은 컴파일러가 반복문으로 바꿔 주므로 언제나 성립하지만, 상호 재귀처럼 다른 함수로 넘어가는 꼬리 호출은 컴파일러 옵션 --tailcalls+ 가 켜져 있어야 한다. dotnet fsi 와 Release 빌드는 켜져 있고 Debug 프로젝트 빌드는 --tailcalls- 이므로, 같은 코드를 프로젝트에 옮겨 Debug 로 돌리면 1000만에서 스택을 넘긴다.`

- [11-recursion.md:101, 552] `누적값의 초기값은 그 연산의 항등원이다` — 챕터 안에서 자기모순이다.
  같은 챕터의 `stepWays` 초기값 `(1L, 1L)` 은 어떤 연산의 항등원도 아니고 점화식의 시작 두 항이다.
  단정문을 조건절로 낮춰야 한다.
  101줄 교체:
  `누적값이 하나의 연산으로 값을 이어 붙이는 꼴이면 초기값은 그 연산의 항등원이다. 곱셈이면 1, 덧셈이면 0 이다. 5챕터에서 List.fold 의 초기값을 정할 때와 똑같은 기준이다. 점화식의 시작 값을 나르는 누적값은 여기서 벗어난다(뒤의 stepWays 가 그 경우다).`
  552줄 교체:
  `누적값을 하나의 연산으로 이어 붙일 때 초기값은 그 연산의 항등원이다. 곱셈은 1, 덧셈은 0, 문자열 이어 붙이기는 "" 다. List.fold 의 초기값을 정하는 기준과 같다. 점화식의 시작 값을 담는 누적값은 예외이고 stepWays 의 (1L, 1L) 이 그 예다.`

- [11-recursion.md:388, 433] `Map` 을 "사전"으로 풀어 썼다. 용어집 `Map` (collection type) 행이
  `"맵"·"사전" 쓰지 않음` 으로 확정돼 있고, `Map` 이 실제로 쓰이는 챕터는 11챕터가 처음이므로
  이 챕터가 표기를 세운다. 388줄은 `Map` 이 무엇인지 처음 소개하는 자리이기도 하니 성질도 함께 적는다.
  388줄 교체:
  `원서는 CSV 파일을 읽어 Map<string, Connection list> 로 만든다. 왜 리스트가 아니라 Map 인지가 이 절의 요점이다. Map 은 키-값 쌍을 담는 불변 컬렉션이고, 이 데이터에 던질 질문이 "이 지점에서 갈 수 있는 곳은?" 이므로 키로 바로 찾는 Map 이 맞는 모양이다.`
  433줄 교체(해당 절만): `마지막의 List.groupBy 로 출항지별로 묶고 Map.ofList 로 Map 을 만든다.`

## 개선 권장

- [11-recursion.md:157] `Repeated 261440 times:` — 이 숫자는 실행마다 바뀐다. 재실측 세 번에
  261625 / 261571 / 261521 이 나왔다. 인용을 `Repeated 261440 times:` 처럼 고정 숫자로 두면
  독자가 자기 출력과 다른 것을 이상하게 여긴다. `Repeated ... times:` 로 줄이거나
  "26만 번대의 반복 횟수" 로 풀어 쓰는 편이 낫다. 뒤에 이미 "숫자 자체를 외울 것은 아니다"가 있어
  문맥은 맞다.

- [11-recursion.md:336, 557] 퀵소트 시간 실측값이 이 저장소에서 재현되지 않는다.
  재실측: 무작위 2만 개 0.14~0.18초(연속 3회), 정렬된 1만 개 3.49초, 2만 개 12.28초,
  4만 개 54.74초. 제곱 규모라는 결론과 "두 배면 네 배" 서술은 그대로 맞지만 0.07초/4.0초/14.4초는
  0.15초/3.5초/12.3초로 갱신하거나 자릿수 규모로 적는 편이 안전하다.
  더 중요한 것은 "스택이 아니라 시간이 먼저 문제"라는 판단인데 이것은 정확하다. 근거를 한 문장
  넣어 두면 독자가 "왜 스택 오버플로라고 안 쓰나"를 묻지 않는다. 실측 근거는 이렇다 —
  정렬된 10만 개를 끝까지 돌려 봤더니 재귀 깊이 10만으로 378.9초(6분 19초)에 스택 오버플로 없이
  정상 종료했다(종료 코드 0). 4만 개는 54.7초였다. 깊이를 더 키우려면 매 단계가 남은 원소를 전부
  훑으므로, 스택 한계(같은 노트의 소박한 재귀는 26만 프레임에서 죽었다)에 닿기 전에 시간이 먼저
  막는다. 집필자가 "6분 넘게 미완"으로 본 것은 정확히 이 6분 19초짜리 실행을 중간에 끊은 것이다.
  추가 문장 예:
  `깊이가 원소 수만큼 깊어지지만 스택보다 시간이 먼저 막는다. 정렬된 10만 개는 재귀 깊이 10만으로 6분 19초를 쓰고도 스택 오버플로 없이 끝났다. 깊이를 더 키우려면 매 단계가 남은 원소를 다 훑기 때문에, 스택 한계에 닿기 전에 실행 시간이 먼저 손을 든다.`

- [11-recursion.md:15] `패턴 매칭으로 갈래를 적는 것이 관례인데, 갈래가 빠졌는지 눈으로 확인하기
  쉽기 때문이다` — 근거를 컴파일러로 올릴 수 있다. 와일드카드 없이 갈래를 열거하면 빠진 갈래를
  컴파일러가 경고 FS0025 로 알려준다(실측: 기저 경우를 지우고 `| n when n > 1 ->` 만 남기면
  `warning FS0025: 이 식의 패턴 일치가 완전하지 않습니다...`). 5챕터의 빠짐없는 패턴 매칭과
  이어지는 대목이니 한 절로 바꾸는 것을 권한다.

- [11-recursion.md:97] 꼬리 호출 정의를 재귀 호출로 좁혀 놓았다. 바로 뒤 상호 재귀 절이
  자기가 아닌 다른 함수로 가는 꼬리 호출을 다루므로 정의와 어긋난다. 한 절만 늘려라:
  `함수가 마지막으로 하는 일이 어떤 호출이고 그 결과가 곧 그 함수의 반환값이면, 즉 호출이 돌아온 뒤에 할 일이 남지 않으면 그 호출을 꼬리 호출(tail call)이라고 한다. 재귀 호출일 필요는 없다.`

- [11-recursion.md:221] `리스트를 머리 :: 나머지 로 분해한다` — 7챕터는 같은 패턴을
  `머리 :: 꼬리` 로 적었고 용어집 `tail`→꼬리가 확정돼 있다. 개념 이름은 꼬리로 두고 변수 이름만
  `rest` 로 두는 것이 이 절의 의도에도 맞다. 교체 문장:
  `이 절에서 리스트를 머리와 꼬리로 분해한다. 리스트의 꼬리(tail)와 꼬리 재귀의 "꼬리"는 글자만 같고 다른 말이다. 앞은 머리를 뗀 나머지 리스트이고, 뒤는 함수 본문에서 재귀 호출이 놓인 자리를 가리킨다. 헷갈리지 않게 이 노트는 분해한 나머지를 rest 로 적는다.`

- [11-recursion.md:378] `depth` 의 `List.max` 는 부분 함수다. 자식이 빈 `Node` 를 넣으면
  예외가 난다(이 노트의 `expandRoutes` 는 그런 값을 만들지 않으므로 예제는 안전하다).
  뒤에서 `Map.find`·`List.minBy` 를 부분 함수로 짚어 두었으니 여기도 한 절 붙이면 계열이 맞는다:
  `자식이 없는 Node 를 만들면 List.max 가 예외를 던진다. 이 노트의 트리는 그런 값을 만들지 않는다는 전제가 깔려 있다.`

- [11-recursion.md:555] `리스트 하나를 훑는 일이라면 fold 를 먼저 고르는 것이 낫다` — 5챕터는
  "전용 집계 함수 → filter/map/choose → fold" 순으로 고르라고 못 박았다(05-collections.md:203, 446).
  비교 대상을 밝히지 않으면 두 챕터가 어긋나 보인다. 교체 문장:
  `리스트 하나를 훑는 일이라면 직접 재귀보다 fold 가 먼저다. 전용 집계 함수가 있으면 그것이 먼저라는 5챕터의 순서는 그대로다.`

- [11-recursion.md:275 근처] `List.fold` 로 다시 쓰기 절에서 `reduce` 를 언급하지 않았다.
  5챕터가 `reduce` 를 확실히 세워 뒀으므로 왜 여기서는 못 쓰는지 한 절 붙이면 연결이 좋아진다.
  상태가 `string` 이고 원소가 `(int * string)` 이라 타입이 갈리므로 `reduce` 는 아예 후보가 아니다
  (`reduce` 는 상태와 원소의 타입이 같아야 한다). `reduction` 이라는 이름을 여기서 다시 쓸 필요는 없다.

- [11-recursion.md:437 절 도입부] 원서 오기를 한 줄 각주로 남기는 것을 권한다. 원서 p.148 의
  `getUnvisited` 주석은 `// Connection list -> Waypoint -> Waypoint list` 인데 p.151 완성 코드는
  `// Map<string, Connection list> -> Waypoint -> Waypoint list` 로 다르고, 본문 서술도
  "We pass in the Map of Connections" 라고 적혀 있다. 실제 호출이
  `getUnvisited routeMap[current.Location] current` 이므로 첫 인자는 `Connection list` 이고
  p.148 쪽이 맞다. 집필자 판단이 정확하다. 원서를 옆에 두고 읽는 독자에게는 이 한 줄이 값을 한다.
  예: `원서 p.148 의 주석은 Connection list 로, p.151 완성 코드의 주석은 Map<string, Connection list> 로 서로 다르다. 실제 인자는 Map 에서 꺼낸 리스트이므로 앞쪽이 맞다.`

- [11-recursion.md:212] 넘침 대응으로 `bigint` 와 상한 검사만 적었다. 검사 연산자로 바꾸는 길도
  있다. 실측: `open Microsoft.FSharp.Core.Operators.Checked` 를 켜면
  `System.Int64.MaxValue + 1L` 이 `OverflowException` 을 던진다. 한 절 덧붙일 만하다.

- [11-recursion.md:449, 469] `nextHops legs current` 는 인자 순서 때문에 파이프에 바로 얹히지 않아
  `|> fun legs -> nextHops legs current` 어댑터가 필요하다. `nextHops current legs` 로 뒤집으면
  `|> nextHops current` 한 칸으로 줄고, 같은 노트가 `eventsAt plan showNo` 에서 설명한
  "변하지 않는 것을 앞에" 원칙과도 맞는다. 다만 지금 순서는 원서 `getUnvisited connections current`
  를 그대로 따른 것이므로 대조 편의를 택한 것이라면 그대로 두어도 된다. 판단만 명시하라.

- [11-recursion.md:365 근처] 자식을 `list` 로 잡은 이유를 "지연 평가가 필요 없고" 로 적었다.
  원서 `seq` 와의 차이가 마지막 절의 완전 탐색 한계 서술과 이어진다. 원서 판은 트리를 훑는
  만큼만 만들고, 이 노트 판은 트리 전체를 먼저 다 만든다. 한 절로 짚어 두면 "후보 수가 지수로
  불어난다"는 뒤 서술이 더 구체적으로 읽힌다(선택).

- [11-recursion.md:8] 도메인 열거에 트리 순회 예제(창고 구역)와 상호 재귀 예제(주간조/야간조)가
  빠져 있다. `응답 시간` 은 7챕터 로그 파싱 절에도 나오지만 그쪽은 도메인이 다르고 이 노트는
  `latency` 정수 리스트 하나이므로 충돌로 보지 않는다.

개념 서술 중 정확하다고 확인한 것.

- 꼬리 호출의 인과가 두 절에 걸쳐 옳게 깔려 있다. 43줄이 "돌아오면 할 일"이 살아 있어야 하는
  이유로 스택 프레임을 도입하고, 97~99줄이 그 할 일이 없어지면 프레임을 쌓지 않는다로 잇는다.
  전개도(`orderCount 4` 두 판)가 괄호의 유무로 그 차이를 눈에 보이게 만든 것이 특히 좋다.
  누적값이 왜 꼬리 호출을 만드는지(기저 경우가 `1L` 이 아니라 `acc` 를 돌려준다는 지적)도 정확하다.
- 상호 재귀는 `let rec` + `and` 가 맞고, F# 이 위에서 아래로 이름을 확인한다는 설명도 맞다.
- `StackOverflowException` 이 `try ... with` 로 잡히지 않고 프로세스를 끝낸다는 서술은 정확하다.
  종료 코드 134 까지 재현된다.
- `List.partition` 시그니처와 "순서를 지킨 채 튜플로 돌려준다"가 맞다. 기준값을 `rest` 에서만
  나눠야 재귀가 끝난다는 지적도 맞다(`values` 를 `<=` 로 나누면 한 원소 리스트에서도 무한히 돈다).
- `quickSort` 의 자동 일반화 결과가 `values: 'a list -> 'a list when 'a: comparison` 이고
  노트 주석과 같다. `quickSort latency = List.sort latency` 도 `true` 다.
- `fold` 서술이 5챕터와 어긋나지 않는다. `folder` 의 첫 매개변수가 누적값, 둘째가 원소라는 것,
  초기값이 항등원이라는 기준, `List.fold` 가 반복문으로 구현돼 있다는 것 전부 맞다
  (300만 원소 `List.fold` 가 스택 문제 없이 돈다).
- 원서 p.145 두 번째 `fold` 변형을 코드로 옮기지 않고 한 단락으로 축약한 판단은 타당하다.
  그 변형의 요지(초기값을 `string n` 으로 두고 `acc = string n` 인지로 "이미 붙었는지"를
  따진다)를 정확히 요약했고, 코드로 옮겨도 새 개념이 없다.
  프로세스에서 언급한 `List.iter (eventsAtFold eventPlan >> printfn "%s")` 도 실제로 컴파일되고
  같은 결과를 낸다(확인함).
- 스택을 터뜨리는 코드에 `id` 를 붙이지 않은 처리가 옳다. `id` 가 붙은 다섯 단위에는 프로세스를
  죽이는 코드도, 오래 걸리는 코드도 없다(가장 느린 `11-tree` 가 3.4초, 나머지 2.7~2.8초).
  `id` 없는 블록 셋(FS0039 / FS0576 / `orderCount (-1)`)과 `sumHoursNaive` 블록은 모두
  의도한 대로 동작한다 — 오류 블록은 적어 둔 오류 코드가 실제로 나고, 죽는 블록은 죽는다.
  독자가 직접 터뜨려 볼 정보(어떤 함수에 어떤 입력, 무엇이 찍히고 종료 코드가 얼마인지)도 충분하다.
- `Tip`/`Leaf` 가 "도착지에 닿은 것"과 "막다른 길"을 겸하는 점을 말단 23개 대 완주 17개로
  드러낸 처리는 학습에 도움이 된다. 원서는 가지를 멈추는 두 경우를 p.149 에서 말하기는 하지만
  그 결과로 말단에 두 종류가 섞인다는 것과 그래서 필터가 필요하다는 인과를 잇지 않는다.
  노트가 숫자로 그 인과를 보인 것이 원서보다 낫다. `Voyage` 레코드를 누적값으로 부르고
  `grow` 의 초기 인자를 `loop n 1L` 과 같은 자리라고 짚은 것도 챕터 전체를 하나로 묶는다.
- 도메인을 갈아 끼운 `11-fold` 단위는 어색한 곳이 없다. 규칙 목록 `(주기, 행사 이름)` 이
  원서의 `(나누는 수, 붙일 말)` 구조를 그대로 담고, 12회차에서 두 이름이 이어 붙는 것을
  집어 준 것이 FizzBuzz 의 15 자리와 같은 역할을 한다. 출력 두 줄과 `List.forall` 대조
  결과가 실측과 일치하고, 다른 챕터와 도메인 낱말이 겹치지 않는다.
- `Map.tryFind` + `Option.defaultValue []` 로 원서의 인덱서 접근을 바꾼 것과 그 이유
  (부분 함수, 부분 적용과 무관하다는 단서)가 용어집 규칙대로 적혀 있다.
