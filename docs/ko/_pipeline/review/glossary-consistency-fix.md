## 2. 고친 행

### 2.1 `do!` — 어순이 한 행 안에서 갈렸던 것 (지시받은 항목)

행 앞머리의 서술문은 "효과가 감싼 `unit`", 행 끝의 지시문은 "`unit` 을 감싼 효과" 였다.
`Async<unit>` 은 `Async` 라는 효과가 `unit` 을 감싼 것이므로 서술문 쪽이 옳다.
12챕터 노트 두 곳(507줄·623줄, 최종 검수 보고서의 490·606줄은 그 뒤 편집으로 밀린 번호다)이
서술문 문면을 글자까지 따르고 있어 노트가 맞고 지시문이 틀렸다.

고친 부분 — 행 끝의 지시문 한 문장만 교체했다.

바꾸기 전:
```text
"`unit` 을 감싼 효과" 로 쓴다.
```
바꾼 뒤:
```text
"효과가 감싼 `unit`" 으로 쓰고 어순을 뒤집어 "`unit` 을 감싼 효과" 로 적지 않는다 — 감싸는 쪽이 `Async`·`Result` 같은 효과이고 감싸이는 쪽이 `unit` 이다.
```

지시문을 서술문과 같은 문면으로 맞추면 같은 말이 한 행에 두 번 오게 되므로, 뒤집힌 어순을
금지 표기로 못박는 형태로 적었다. 이렇게 하면 뒤집어 쓴 원고를 검수에서 잡을 수 있다.

같은 계열 행의 어순도 확인했다. `effect`(값을 한 겹 감싸), `asyncResult`(`Async` 가 `Result` 를
감싼 순서다), `let!`(감싼 값이 그대로 묶여), `return!`(이미 효과가 감싼 값), `unwrap`,
`underlying type`, `base type`, `applicative` 는 전부 "감싸는 쪽 + 가 감싼 + 감싸이는 쪽" 순서다.
어순이 뒤집힌 자리는 `do!` 행의 지시문 하나뿐이었다.

### 2.2 `host` — 같은 낱말을 금지하고 곧바로 허용했던 것 (새로 찾음)

`do!` 와 같은 갈래다. 한 행에서 "호스팅" 을 금지 표기로 적어 놓고 다음 문장에서 조건부로 허용했다.
읽는 쪽이 어느 규칙을 따라야 하는지 알 수 없다.

바꾸기 전:
```text
"숙주"·"호스팅" 쓰지 않는다. 동작을 가리킬 때만 "호스팅" 을 쓴다.
```
바꾼 뒤:
```text
"숙주" 쓰지 않는다. 명사는 "호스트" 로 쓰고, 앱을 띄워 두는 동작이나 그 방식을 가리킬 때만 "호스팅" 을 쓴다("호스팅 모델").
```

금지 목록에서 "호스팅" 을 빼고 갈라 쓰기 규칙 한 줄로 합쳤다. 괄호의 실례는 같은 용어집
`web root` 행이 이미 "이 호스팅 모델에서" 로 쓰고 있는 자리에서 가져왔다 — 고치기 전 규칙대로면
용어집 자신이 금지 표기를 쓰고 있는 셈이었다.
노트 쪽은 13·14·15챕터에 "호스트" 만 나오고 "호스팅" 은 한 번도 없다(`grep` 확인). 노트 무수정.

### 2.3 `model binding` — 행이 스스로 금지한 줄임형을 자기 설명에서 쓴 것 (새로 찾음)

행 끝이 "바인딩" 단독 사용을 금지하는데, 같은 행의 설명 문장이 "바인딩은 빠진 필드를 …" 으로
그 줄임형을 쓰고 있었다. 기확정 `binding`→바인딩(`let` 바인딩)이 있어 실제로 겹쳐 읽히는 낱말이다.

바꾸기 전:
```text
검증과 구별해 쓴다 — 바인딩은 빠진 필드를
```
바꾼 뒤:
```text
검증과 구별해 쓴다 — 모델 바인딩은 빠진 필드를
```

14챕터 노트는 다섯 곳 모두 "모델 바인딩" 온낱말이다(`grep` 확인). 노트 무수정.

### 2.4 `header row` — 두 행이 서로 다른 규칙을 적고 있던 것 (지시받은 항목, 3절에 판단 근거)

바꾸기 전:
```text
| header row | 헤더 줄 | 구분자 텍스트의 첫 줄. MS ko 계열의 "머리글 행" 쓰지 않음. 문맥이 분명하면 "헤더"로 줄여 쓴다 |
```
바꾼 뒤:
```text
| header row | 헤더 줄 | 구분자 텍스트의 첫 줄. MS ko 계열의 "머리글 행" 쓰지 않음. `header (HTTP)`→헤더 가 등재되어 같은 낱말이 두 개념을 가리키므로 "헤더" 로 줄여 쓰지 않고 언제나 온낱말로 적는다(기확정 `effect`/`side effect`, `pipeline`/`middleware pipeline` 과 같은 갈라 쓰기 규칙). 6·11챕터 |
```

표기는 기확정 "헤더 줄" 을 그대로 두었다. 챕터 표시를 붙여 다른 행과 형식을 맞췄다.

## 3. `header row` 처리 판단과 근거

### 무엇이 문제였나

- `header row`(기확정, 배치 A 계열)는 "문맥이 분명하면 「헤더」로 줄여 쓴다" 였다.
- `header (HTTP)`(배치 D 신규)는 "그쪽은 언제나 「헤더 줄」 온낱말로 적는다" 였다.
  같은 개념에 두 행이 정반대 규칙을 적어 둔 상태다. 지시받은 `do!` 와 같은 갈래의 불일치인데
  한 행이 아니라 두 행에 걸쳐 있었다.
- 그리고 기확정 표기 "헤더 줄" 이 노트 16개 전체에서 한 번도 쓰이지 않았다(`grep` 확인).
  6·11챕터의 CSV 첫 줄이 모두 "헤더" 또는 "헤더 한 줄" 이다.

### 세 갈래 가운데 무엇을 택했나

1. 표기를 "헤더" 로 낮추고 `header row` 행을 없애거나 병합한다 → 기각.
   기확정 표기를 뒤집는 일이고, 웹 챕터의 HTTP 헤더와 영어 키·한국어 표기가 함께 겹친다.
2. 비고만 고쳐 줄임형을 계속 허용하고 `header (HTTP)` 쪽 문장을 물린다 → 기각.
   기확정 표기가 노트 어디에도 쓰이지 않는 죽은 항목으로 남는다. 용어집은 노트가 따르는 표기를
   적는 문서이므로, 아무도 쓰지 않는 표기를 등재한 채 두면 다음 챕터에서 같은 혼선이 되풀이된다.
3. 온낱말 규칙으로 통일하고 6·11챕터 네 곳을 고친다 → 택했다.

근거는 셋이다.
- 용어집에 이미 같은 판례가 셋 있다. `effect`/`side effect`, `tail`/`tail recursion`,
  `pipeline`/`middleware pipeline` 은 모두 "낱말이 겹치는 쪽은 반드시 온낱말" 로 정리돼 있다.
  `header (HTTP)` 행이 쓴 문장도 그 판례를 그대로 따른 것이다. 판례가 있는 자리에서 예외를
  하나 더 만들 이유가 없다.
- 고칠 곳이 네 곳뿐이고 전부 산문과 주석이다. 코드 식별자·출력 기댓값에 걸리는 곳이 없어
  실행 단위를 다시 돌릴 필요가 없다.
- 배치 D 병합 보고서 6.1 이 같은 결론으로 치환문까지 만들어 두었다. 그 목록을 그대로 잇는다.

### 남는 사실 하나

6·11챕터에는 HTTP 가 한 줄도 나오지 않고, 13·14·15챕터에는 구분자 텍스트가 나오지 않는다.
한 챕터 안에서 두 개념이 부딪히는 자리는 지금 없다. 그래서 이 처리는 기술 오류를 고치는 것이
아니라 노트 전체에서 낱말 하나가 한 개념만 가리키게 만드는 표기 통일이다. 적용 우선순위는
낮게 잡아도 된다. 다만 규칙을 하나로 정한 뒤에는 용어집과 노트가 어긋난 상태로 남으므로,
적용하지 않기로 결정한다면 `header row` 행의 비고를 다시 물려야 한다.

## 5. 불일치가 없다고 확인한 것

- 계산 식 계열 행의 감싸기 어순 — 2.1 에 적은 여덟 행 전부 한 방향이다.
- 표기 칸과 비고의 지시문이 어긋난 행 — 333행을 기계적으로 훑어 인용부호 뒤에 "쓴다"·"적는다"·
  "통일한다"·"고정한다" 가 오는 자리를 모두 뽑아 표기 칸과 비교했다. `do!` 를 고친 뒤 남은 것은
  `indexer`("대괄호 인덱서"), `overload`("오버로드 해결"), `exception`("던진다"),
  `unwrap`("감싸") 넷인데 모두 표기의 파생형이나 짝 낱말을 가리키는 정상 서술이다.
- 금지 표기와 허용이 한 행에서 부딪힌 자리 — `host` 를 고친 뒤 남은 것이 없다.
  `service location`(패턴 이름일 때만 "서비스 로케이터"), `master page`(F# 코드를 설명하는
  자리에서는 "공용 레이아웃"), `payload`("응답 본문" 으로 풀어 쓰기 허용)는 셋 다 예외의 범위를
  먼저 적고 그 밖을 금지한 형태여서 규칙이 하나로 읽힌다. 노트 쪽 실제 사용도 이 규칙과 맞는다
  (15챕터는 "공용 레이아웃" 을 쓰고 "마스터 페이지" 는 다른 뷰 엔진을 가리키는 한 곳에만 나온다).
- 줄임형을 허용한 다른 행(`forward pipe operator`→"파이프 연산자",
  `function composition operator`→"합성 연산자", `guard clause`→"`when` 가드",
  `dependency injection`→"컨테이너", `computation expression builder`→"빌더")은 줄인 낱말이
  다른 등재 항목과 겹치지 않는다. `compose operator (>=>)` 는 한국어 이름을 붙이지 않기로 해
  두어 `>>` 의 "합성 연산자" 와 부딪히지 않는다(노트에서 "합성 연산자" 는 02챕터의 `>>` 한 곳뿐).
- "핸들러 함수"·"처리기" 처럼 새로 금지된 표기가 노트에 남아 있는지도 훑었다. 0건이다.
