## 2. 표기 충돌과 결정

### 2.1 서문 노트를 본문에서 가리키는 표기 — `서문 챕터` 로 확정

두 전문가가 반대로 권고한 항목이다. 결론은 17챕터 전문가 쪽, 곧 `서문 챕터` 다.
16챕터 전문가의 `서문 노트` 는 채택하지 않는다.

실측한 관례가 근거다. 노트 18개에서 다른 노트를 가리키는 형태를 세면 이렇다.

| 형태 | 출현 | 어디 |
|---|---|---|
| `N챕터` | 320회 | 18개 노트 전부 |
| `N챕터 노트` | 10회 | 17챕터 7회, 07·09·16챕터 각 1회 |
| 본문에 노트 파일 이름 | 2회 | 17챕터 3·19행이 전부 |
| `서문 챕터` | 4회 | 16챕터 13·18·38·43행 |
| `서문 노트` | 1회 | 17챕터 19행 |
| `00챕터`·`0챕터` | 0회 | 없다 |

판단은 셋이다.

1. 관례가 `N챕터` 다(320대 10). `서문 챕터` 는 이 계열에 그대로 들어가고 `서문 노트` 는
   계열 밖으로 나간다. STYLE.md 가 `N챕터` 통일을 못박아 둔 것과도 맞는다.
2. `서문 노트` 표기는 파일 이름 병기와 한 몸으로 올라왔다. 본문에 노트 파일 이름을 적은 자리는
   18개 노트에서 17챕터 두 곳이 전부다. 하나뿐인 이탈례를 관례로 굳힐 근거가 없다.
   16챕터 전문가가 "17챕터 선례" 라고 부른 것은 선례가 아니라 유일례다.
3. 수정량도 같은 방향이다. `서문 챕터` 로 정하면 17챕터 1곳, `서문 노트` 로 정하면 16챕터 4곳을
   고친다.

16챕터 전문가가 든 반대 근거 둘은 결론을 뒤집지 못한다.
- "00 노트에 원서 챕터 번호가 없고 게이트가 숫자와 장을 붙인 형태를 막는다" — 맞다. 그래서
  번호로 부를 수 없다. `서문 챕터` 는 번호를 쓰지 않으므로 이 제약에 걸리지 않는다.
- "한 낱말이 노트와 원서 두 대상을 가리킨다" — 맞다. 다만 이 문제는 노트 쪽 표기를 무엇으로
  하든 남으므로, 원서 쪽을 `원서 서문` 으로 갈라 쓰는 규칙이 해법이다. 그 규칙은 그대로 채택했고
  용어집 `preface` 행에 담았다.

확정 규칙(용어집 `preface` 행).
- 노트 `00-preface-getting-started.md` 를 가리킬 때는 `서문 챕터`. 파일 이름을 병기하지 않는다.
- 원서 pp.1-2 를 가리킬 때는 `원서 서문`.
- 원서 서문의 범위는 pp.1-2 다. FSI·중단점 이야기가 있는 Getting Started(원서 p.6)를
  `원서 서문` 에 넣지 않는다.

이 결정에 따라 16챕터 전문가 보고서의 교체문 두 개를 병합자가 고쳐 적었다(5.1 의 16-1·16-6).
원안이 `서문 노트(00-preface-getting-started.md)` 를 쓰고 있어 그대로 적용하면 확정 표기와
어긋난다. 16챕터 18행은 이 결정으로 손댈 필요가 없어졌고, 43행은 5.2 에서 다르게 처리했다.

### 2.2 두 후보가 같은 낱말을 올린 것

| `preface` / `preface chapter` | 서문 + "서문 노트"(16) / 서문 챕터(17) | `preface` 한 행, 표기 `서문 챕터` | 2.1. 영어 키는 `preface` 를 택했다. 확정 대상이 낱말 자체이고 `preface chapter` 는 그 낱말의 한국어 지칭 규칙이라 별개 표제어로 세울 이유가 없다 |

### 2.3 `store` — 등재한다. 본문 수정은 없다

13~15챕터가 이미 "저장소" 로 쓰는데 용어집에 없던 항목이다. 16 후보의 지적이 맞고,
13·14·15 후보 파일에 이 행이 없는 것도 확인했다. 등재했다.

실측하며 한 가지를 더 담았다. "저장소" 가 노트에서 두 뜻으로 쓰인다.

| 뜻 | 어디 | 곳 |
|---|---|---|
| 데이터를 담는 클래스(`InspectionStore`) | 10·12·13·14·15·16챕터 | 10챕터 2, 12챕터 1, 13챕터 2, 14챕터 31, 15챕터 18, 16챕터 6 |
| 이 프로젝트의 git 저장소 | 서문 챕터·06·11챕터 | 서문 챕터 5, 06챕터 2, 11챕터 4 |

두 뜻이 한 단락에 오는 자리는 없다. 그래서 본문을 고칠 곳이 없고, 헷갈릴 자리에서는
"점검 기록 저장소" 처럼 무엇을 담는지 붙여 적는 규칙만 비고에 담았다.
04챕터 152행의 "리포지터리" 한 곳은 원서가 든 계층 이름을 열거한 자리이므로 그대로 둔다는
예외도 함께 적었다.

### 2.4 `loop` — 등재한다. 본문 수정은 없다

실측하면 갈린 것이 아니라 이미 규칙대로 쓰이고 있다.

| 낱말 | 곳 | 쓰임 |
|---|---|---|
| `for` 루프 | 05챕터 3행 1곳 | 키워드를 짚는 자리 |
| 반복문 | 11챕터 98·99·295·562행, 16챕터 26행 | 파이프라인·재귀와 견주는 자리 |
| "루프" 단독 | 0곳 | 없다 |

16 후보가 올린 규칙(일반 명사는 "반복문", 키워드를 짚을 때만 `for` 루프)이 실제 용례와 정확히
맞는다. 그대로 등재했고 5챕터도 16챕터도 고칠 곳이 없다.

### 2.5 조건부 `taskResult` — 등재한다

16챕터 76행을 `asyncResult` 에서 `taskResult` 로 바로잡으라는 지적이 확정되었으므로(5.1 의 16-2)
조건이 충족됐다. 병합자가 FSI 로 다시 실측해 근거를 확인했다.

```
taskResult  : Task<Result<int, DbError>>
asyncResult : Async<Result<int, DbError>>
```

`fetch : int -> Task<Result<string, DbError>>` 를 두고 두 계산 식에서 `let! v = fetch k` 를
똑같이 적어 얻은 결과다. `asyncResult` 도 `Source` 오버로드로 `Task<Result<..>>` 를 받아
컴파일되지만 결과가 `Async<Result<..>>` 라서, `Task` 를 요구하는 핸들러 자리에서는 `taskResult`
쪽이다. 16챕터 전문가의 실측과 일치한다.

### 2.6 병합자가 판단한 것

- `solution file`·`solution folder` 를 기확정 `solution` 행의 하위 항목으로 등재했다.
  17 후보가 "`solution` 행 비고에 두 항목을 가리키는 한 줄을 넣자" 고 남겼으나 채택하지 않았다.
  기확정 행을 건드리지 않는 쪽을 택하고, 대신 새 두 행의 비고에서 위쪽 `solution` 행을 가리켰다.
  세 행이 알파벳 순으로 붙어 있어 찾는 데 문제가 없다.
- `CLI` 행의 용례를 17챕터로 좁혔다. 17 후보는 "14·17챕터" 로 적었으나 14챕터의 `CLI` 두 곳은
  `[<CLIMutable>]` 특성 이름이고 `dotnet` CLI 와 무관하다(실측). 비고에 그 구분을 적어 두었다.
- `BOM` 행에 `.sln` 을 보탰다. 17 후보는 `.fs`·`.fsproj` 에 BOM 이 있고 `.slnx` 에 없다고만 적었다.
  병합자가 재실측하니 `-f sln` 으로 만든 `.sln` 에도 BOM 이 있다(`ef bb bf`).
- `locale` 행에 기확정 `culture`(문화권)와의 경계를 적었다. 로케일은 셸·프로세스의 메시지 언어
  설정이고, `CultureInfo` 쪽은 `culture` 행이 맡는다.
- `resource (learning material)` 행에 인용 예외를 적었다. 10챕터 705행의 `warning FS0760` 인용에
  "리소스" 가 들어 있는데, 컴파일러 메시지 인용은 원문 표기를 유지하므로 위반이 아니다.
- `F# Software Foundation` 행에서 약어 FSSF 를 쓰지 않기로 한 16챕터 판단을 그대로 담았다.
  기확정 `dependency injection`(DI)·`tail call optimisation`(TCO) 판례와 같다.
- 용어집 비고에서 00 노트를 가리키는 표현을 `서문 챕터` 로 적었다. 지금까지 용어집이 00 노트를
  가리킨 자리는 없었으므로(실측 0회) 이 결정을 처음 쓰는 자리다.

## 3. `[기확정 변경 제안]` — 1건, 적용하지 않았다

병합 모드 규칙대로 적용하지 않고 여기에 모았다. 사람이 판단할 항목이다.

### 3.1 `exit code` 비고 확장 (17 후보)

현재 행.

```
| exit code | 종료 코드 | `main` 이 마지막에 돌려주는 `int`. 0 이 성공. "반환 코드" 쓰지 않음 |
```

제안 내용. 표기는 그대로 두고 비고에 "CLI 프로세스가 셸에 돌려주는 값도 같은 말로 부른다" 를
덧붙이자는 것이다. 17챕터가 `dotnet new sln` 의 종료 코드 73 을 같은 낱말로 부르고, 11챕터
158행도 스택 오버플로로 죽은 프로세스의 "종료 코드 134" 를 그렇게 부른다.

병합자 실측. 같은 자리에서 `dotnet new sln` 을 두 번 돌리면 두 번째가 73 으로 끝난다.
안내 메시지에 `refer to https://aka.ms/templating-exit-codes#73` 이 붙는다.

병합자 의견은 승인 쪽이다. 표기를 바꾸지 않으므로 앞 챕터 본문을 고칠 곳이 0 이고, 배치 D 가
같은 성격의 비고 확장 4건을 "앞 챕터 본문 파급이 없다" 는 이유로 적용한 판례가 있다.
다만 이번 지시가 `[기확정 변경 제안]` 을 적용하지 말라고 못박았으므로 판단을 넘긴다.
승인하면 아래 한 행으로 갈아 넣으면 된다.

```
| exit code | 종료 코드 | `main` 이 마지막에 돌려주는 `int`. 0 이 성공. 프로세스가 셸에 돌려주는 값도 같은 말로 부른다 — 스택 오버플로로 죽은 `dotnet fsi` 가 134(11챕터), 덮어쓰기 확인을 요구하며 멈춘 `dotnet new sln` 이 73(17챕터, 실측)이다. 컴파일러 오류 번호(`오류 FS0222`)와는 성격이 다르므로 섞어 쓰지 않는다. "반환 코드" 쓰지 않음 |
```

### 3.2 병합자가 발견한 것 — 제안으로만 남긴다

`assignment operator` 행의 비고가 용례를 "13챕터" 로만 적는데, `<-` 를 처음 다루는 곳은
1챕터 178·181-182·188·608행이다. 기확정 행이므로 손대지 않았다. 5.1 의 16-1 을 적용하면
16챕터 색인이 "가변 바인딩은 1챕터가 `<-` 와 함께 처음 다룬다" 로 바뀌므로, 그때 이 행의
