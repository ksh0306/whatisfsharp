## 2. 표기 충돌과 결정

### 2.1 기반 타입 — `underlying type`(09) vs `base type`(10) → 갈라 쓴다

두 후보가 같은 한국어 표기를 서로 다른 개념에 올렸다. 이번 배치의 유일한 정면 충돌이다.

- 09 후보: `underlying type` → 기반 타입 (단일 케이스 판별 유니온이 감싼 `int`, 타입 약어가 별명을 붙인 타입)
- 10 후보: `base type` → 기반 타입 (`inherit` 로 물려받는 쪽)

결정: `base type` → 기반 타입, `underlying type` → 원래 타입.

근거
- 10 쪽이 상속 계열의 짝 낱말을 이미 쓴다. 기반 타입 ↔ 하위 타입(derived type)이 한 쌍으로 묶이고,
  10 노트 278줄이 `inherit 기반타입(인자)` 이라고 코드 모양까지 그 표기로 적어 놓았다. 이쪽을 옮기면
  노트와 코드 표기가 함께 흔들린다.
- 09 쪽 개념에는 상속이 없다. `Nights of int` 의 `int` 는 물려받은 것이 아니라 감싸인 것이다.
  "기반"을 쓰면 판별 유니온이 `int` 를 상속한다는 오해를 부른다.
- 09 후보 자신이 비고에서 "하부 타입"·"기저 타입"을 subtype 과 헷갈린다는 이유로 기각했다.
  같은 이유가 "기반 타입"에도 그대로 적용된다.
- "원래 타입"은 09 후보의 비고 문장에 이미 들어 있던 낱말이다("...감싼 원래 타입"). 새 조어가 아니다.

영향: 09챕터 4곳(4.5 의 1번). 10챕터 278줄은 고치지 않는다.
`underlying type` 행에 "기반 타입도 쓰지 않는다 — 그 표기는 상속의 base type 쪽이다"를 못 박아 두었다.

### 2.2 `sequence` / `traverse` — 한 행을 두 행으로 갈랐다

08 후보는 두 함수를 한 행에 묶었다. 영어 칸이 `` `sequence` / `traverse` `` 면 정렬 키가 잡히지 않고
`sequence`(시퀀스) 행과 검색이 엉킨다. 그래서 `` `sequence` (function) `` 와 `` `traverse` `` 두 행으로
갈랐고, 컬렉션 타입 `` `Map` (collection type) `` ↔ `` `map` `` 이 쓰는 방식과 같게 맞췄다.
두 행 모두 "서로 뭉개 쓰지 않는다"와 "컬렉션 타입 `seq` 와 상관이 없는 이름"이라는 단서를 담았다.

### 2.3 `capacity` — 영어 칸의 한정어를 영어로 적었다

10 후보의 영어 칸은 `capacity (도메인 상한)` 이었다. 영어 칸에 한국어가 섞이면 정렬 키가 흔들리므로
`capacity (domain limit)` 으로 바꿨다. 한국어 표기(정원)와 비고 내용은 후보 그대로다.

### 2.4 `[<Struct>]` — 한국어 칸을 특성 이름으로 되돌렸다 (이번 세션 정정)

09 후보의 한국어 칸은 "구조체 특성"이었는데, 같은 행 비고가 "특성 이름은 번역하지 않고
`[<Struct>]` 로 쓴다"고 적고 있어 행 안에서 어긋났다. 실측하면 노트도 비고 쪽을 따른다 —
09 노트는 `[<Struct>]` 를 8곳에서 쓰고 "구조체 특성"은 12개 노트 어디에도 없다.
`[<TailCall>]` 행이 한국어 칸에 특성 이름을 그대로 두는 것과도 계열이 맞다.
그래서 한국어 칸을 `` `[<Struct>]` `` 로 고쳤다. 서술문에서 결과물을 가리킬 때 "구조체"를 쓴다는
비고는 그대로 남겼다. 이 정정으로 챕터 수정은 생기지 않는다.

### 2.5 09·10 중복 5행 — 두 챕터가 같은 표기를 올렸다

`access modifier`(접근 지정자), `instance`(인스턴스), `member`(멤버), `property`(프로퍼티),
`static member`(정적 멤버) 다섯 개는 두 후보의 표기가 처음부터 같았다. 표기 결정이 아니라
비고 합치기만 했다. 두 챕터가 갈라 써야 하는 경계는 비고에 남겼다.
- `member` ↔ `property`: 프로퍼티는 멤버의 한 종류다. 프로퍼티 하나를 가리키는 자리에서 "멤버"로 뭉개지 않는다.
- `property` ↔ `field`: 레코드의 필드는 프로퍼티라 부르지 않는다(4.2 의 02챕터 수정이 여기서 나온다).
- `instance` ↔ `object`: 타입에서 만들어 낸 하나만 인스턴스다.

### 2.6 병합이 후보 밖에서 세운 행 2개

| 행 | 이유 |
|---|---|
| `derived type` → 하위 타입 | 10 후보가 `base type` 을 올리며 짝을 "하위 타입(derived type)"이라고 비고에만 적었다. 짝 낱말이 검색되지 않으면 다음 챕터에서 "파생 타입"으로 새어 나간다. 10 노트가 이미 이 표기를 쓰고(3곳), 03 노트 240줄의 subtype 도 같은 표기라 그대로 등재했다 |
| `downcast` → 하향 변환 | 기확정 `upcast`(상향 변환) 행 비고에만 들어 있어 검색이 되지 않았다. 실측하면 `:?>` 는 12개 노트 어디에도 나오지 않고 3·10챕터가 쓰는 것은 상향 변환뿐이므로, 비고에 그 사실을 적어 두었다. 지금 등재하는 이유는 표기가 갈릴 자리를 미리 막는 것이다 |

## 3. 머리말 규칙과 정렬 검증

### 3.1 정렬 키 규칙 — 인계 문서가 지목한 위반 2건의 실제 판정

인계 문서는 `[<Struct>]` 가 `string interpolation` 뒤, `[<TailCall>]` 이 `tail recursion` 뒤에
오는 것을 정렬 위반 2건으로 기록했다. 확인 결과 **두 행의 위치는 옳다.** 위반으로 보인 것은
정렬 키가 `[` 를 문자 그대로 비교했기 때문이다. 특성 표기를 `[<`·`>]` 를 벗긴 안쪽 이름으로
읽으면 두 행은 정확히 제자리에 있다.

- `[<Struct>]` → 키 `struct`. `string interpolation` < `struct` < `struct representation` < `structural equality`
- `[<TailCall>]` → 키 `tailcall`. 공백이 문자 `c` 보다 작으므로 `tail recursion` < `tailcall` < `target framework`

행을 옮기는 대신 규칙을 머리말에 명문화했다. 다음 한 항목을 넣었다.

```
- 표는 영어 칸의 정렬 키로 알파벳 순을 잡는다. 키는 백틱을 벗기고 `[<Struct>]` 같은 특성 표기는
  `[<`·`>]` 를 벗긴 안쪽 이름으로 삼으며 대소문자를 무시한다. 괄호 한정어와 타입 매개변수는
  벗기지 않고, 공백도 문자로 그대로 비교한다. 그래서 `[<Struct>]` 는 `string interpolation` 뒤
  `struct representation` 앞, `[<TailCall>]` 은 `tail recursion` 뒤 `target framework` 앞에 오고,
  `map` 이 `Map` (collection type) 보다, `nullable reference types` 가 `Nullable<'T>` 보다 앞에 온다.
```

괄호 한정어와 타입 매개변수를 벗기지 않는다고 못 박은 것은 `` `map` `` ↔ `` `Map` (collection type) ``,
`sequence` ↔ `` `sequence` (function) ``, `validation` ↔ `` `Validation<'a,'e>` ``,
`nullable reference types` ↔ `` `Nullable<'T>` `` 네 쌍이 모두 같은 규칙으로 놓이게 하기 위한 것이다.
이 키로 252행을 다시 검사해 위반 0건이다.

### 3.2 이식성 규칙 3줄 (08 전문가 권고, 이미 머리말에 들어가 있음)

`#r "nuget: ..."` 을 쓰는 실행 단위는 (1) 버전을 고정하고 (2) `id` 를 떼지 않고
(3) 블록 앞 산문에 선행 요구사항을 한 줄 적는다. 12챕터가 같은 패키지를 쓸 가능성이 높아
챕터 비고가 아니라 머리말 규칙으로 세웠다.

`FsToolkit.ErrorHandling, 5.2.0` 을 이번 세션에서 다시 실측했다. `validation` 계산 식과
`let!`/`and!`, `Validation<'a,'e>` 타입 약어가 그대로 통과한다(로컬 NuGet 캐시에 5.2.0 이 있다).
규칙을 세웠으므로 08 노트가 이 규칙을 지키도록 고쳐야 한다 → 4.4.

  `value type` 세 행이 각각 특성·액티브 패턴 반환 표현·타입 분류를 맡고, 서술문의 "구조체"는
  `[<Struct>]` 행 비고가 허용한다. 단독 행은 세우지 않았다.
- `Validation<'a,'e>` 와 `validation` 계산 식 이름이 한 낱말로 겹치는 문제는 두 행의 비고로
  갈라 두었다. 12챕터가 계산 식을 본격적으로 다룰 때 다시 볼 것.
