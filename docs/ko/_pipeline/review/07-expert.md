# 07챕터 기술 검수 — 액티브 패턴

검수 대상: `docs/ko/07-active-patterns.md` (591줄)
실측 환경: F# Interactive 14.0.111.0 (F# 10.0), .NET SDK 10.
실행 단위 5개(`07-catalog`, `07-trail`, `07-playlist`, `07-query`, `07-accesslog`) 전부 PASS, 경고 0개.
주석에 적힌 기대 출력 33줄을 실제 출력과 한 줄씩 대조했고 전부 일치했다.
집필자가 보고한 실측 8건은 전부 재현했다. 그중 2건은 서술이 실측보다 강하거나 약해 아래에 적었다.

## 수정 필요 (기술 오류)

- [07-active-patterns.md:102] `Blank _` 가 잘못된 표기라는 서술이 틀렸다.
  현재: "`Some ()` 을 반환하는 패턴은 값을 바인딩하지 않으므로 패턴 자리에도 이름만 적는다. `Blank _` 가 아니라 `Blank` 다."
  실측: `Blank`, `Blank ()`, `Blank _` 세 형태가 모두 컴파일되고 같은 결과를 낸다. 반환 타입이 `unit option` 이라 실리는 값이 `()` 이고, `_` 와 `()` 는 그 값에 대한 정상적인 패턴이다.
  인자를 아예 적을 수 없는 것은 `bool` 을 반환하는 부분 액티브 패턴 쪽이다. `Numeric x` 로 적으면 오류가 난다.
  `error FS3868: 이 활성 패턴에는 인수가 필요하지 않습니다. 즉, 'Numeric x' 대신 'Numeric'을(를) 사용해야 합니다.`
  이렇게 고쳐라.
  ```
  - `Some ()` 을 반환하는 패턴은 실어 보낼 값이 없으므로 패턴 자리에 이름만 적는다. 실리는 값이 `()` 이라 `Blank ()` 나 `Blank _` 도 통과하지만, 이름만 적는 쪽이 관용적이다.
  ```
  그리고 `(|Numeric|_|)` 블록(07-active-patterns.md:105-113) 뒤에 이 대비를 한 줄 붙여라. 지금은 블록 안 주석의 "값은 바인딩할 수 없다"가 근거 없이 떠 있다.
  ```
  - `bool` 을 반환하면 실어 보낼 값이 아예 없으므로 패턴 자리에 인자를 적을 수 없다. `Numeric x` 로 적으면 오류 FS3868(`이 활성 패턴에는 인수가 필요하지 않습니다`)이 난다. `unit option` 판과 달리 `Numeric _` 도 받아 주지 않는다.
  ```

- [07-active-patterns.md:577, 07-active-patterns.md:127] `[<return: Struct>]` 를 F# 9 사항으로 묶은 것이 틀렸다.
  `--langversion` 을 낮춰 두 기능을 따로 확인했다.
  - `bool` 반환: F# 9 필요. 8.0 에서 `error FS3350: '부울 반환 및 반환 형식 지향 부분 활성 패턴' 기능은 F# 8.0에서 사용할 수 없습니다. 9.0 이상의 언어 버전을 사용하세요.`
  - `[<return: Struct>]`: F# 6 필요. 5.0 에서 `error FS3350: '활성 패턴에 대한 구조체 표현' 기능은 F# 5.0에서 사용할 수 없습니다. 6.0 이상의 언어 버전을 사용하세요.` 6.0 에서는 통과한다.
  구조체 표현은 2021년 11월 F# 6 에 들어왔으므로 원서 집필 시점에 이미 있었다. 원서가 안 다룬 것은 최신이라서가 아니라 범위 밖으로 뒀기 때문이다.
  577줄을 이렇게 고쳐라.
  ```
  - `[<return: Struct>]` 를 붙이면 부분 액티브 패턴이 `option` 대신 `voption` 을 반환해 힙 할당을 피한다(F# 6 이후). 부분 액티브 패턴이 `bool` 을 반환해도 되는 것은 F# 9 이후다. 원서 시점의 `Some ()` 형태도 그대로 유효하다.
  ```
  127줄의 블록 첫 주석도 고쳐라. 현재 "원서가 '다른 종류도 있다'고 넘긴 것 중 하나다"는 이것이 다섯 번째 종류처럼 읽힌다. 실제로는 부분 액티브 패턴의 표현만 바꾸는 것이고 종류가 늘지 않는다.
  ```
  // 참고 — 새로운 종류가 아니라 부분 액티브 패턴의 반환 표현만 바꾼 것이다. F# 6 이후 쓸 수 있다
  // string -> int voption — 구조체라 힙 할당이 없다
  ```

- [07-active-patterns.md:280] "어느 케이스도 반환하지 않는 경로를 남길 수 없다"가 실측보다 강하다.
  실측: 정의 본문의 `match` 가 불완전해도 컴파일된다. 경고만 난다.
  `warning FS0025: 이 식의 패턴 일치가 완전하지 않습니다.`
  그 경로를 타면 실행 시점에 예외가 난다. `Low`/`High` 두 케이스에서 `High` 를 `| 999 ->` 로만 처리한 정의에 50 을 넣어 확인했다. 예외 타입은 `MatchFailureException` 이다.
  이렇게 고쳐라.
  ```
  - 본문의 마지막 `else Extended` 가 남은 입력 전부를 받는다. 어느 케이스도 반환하지 않는 경로를 남기면 정의 자리에서 경고 FS0025 가 나고, 실제로 그 경로를 타는 입력이 들어오면 실행 시점에 `MatchFailureException` 이 난다. 컴파일이 막아 주지 않으므로 정의 안에서 모든 입력을 처리해 줘야 한다.
  ```

- [07-active-patterns.md:281] "쓰는 쪽에서는 적어야 한다"가 실측보다 약하다. 이 서술은 원서의 지침("Only cases that are used as output should be included")보다 근거가 강한 사실을 놓치고 있다.
  실측: 반환 타입 주석 없이 쓰지 않는 케이스를 이름에 넣으면 정의 자체가 오류다.
  `let (|A|B|C|) (n: int) = if n < 5 then A else B` →
  `error FS1210: 활성 패턴 '|A|B|C|'에 입력으로 확인되지 않는 형식 변수가 포함된 결과 형식이 있습니다. ... 이 문제는 형식 제약 조건을 지정하여 해결할 수 있습니다(예: 'let (|A|B|) (x:int) : Choice<int,unit> = A x').`
  `: Choice<unit,unit,unit>` 로 명시하면 통과하고, 그때는 쓰는 쪽에서 나오지 않는 케이스까지 적어야 한다(빼면 경고 FS0025).
  이렇게 고쳐라.
  ```
  - 출력으로 쓰지 않는 케이스를 이름에 넣으면 그 케이스의 타입을 추론할 근거가 없어 정의 자리에서 오류 FS1210 이 난다. 반환 타입을 `: Choice<unit,unit,unit>` 로 직접 적으면 통과하지만, 그때는 영원히 나오지 않는 케이스를 쓰는 쪽에서 적어야 한다. 실제로 반환하는 케이스만 이름에 적는 것이 맞다.
  ```

- [07-active-patterns.md:279, 07-active-patterns.md:575] 이름 가림 서술이 반대쪽으로 과하게 고쳐졌다.
  집필자가 초안("케이스 이름의 유효 범위는 패턴 자리뿐이라 판별 유니온 케이스와 충돌하지 않는다")을 뒤집은 것은 옳다. 충돌은 실제로 난다. 다만 지금 문장 "이 이름들은 판별 유니온 케이스와 똑같은 방식으로 해석된다"는 과하다. 세 가지를 따로 확인했다.
  1. 패턴 자리에서는 뒤에 정의된 쪽이 앞의 것을 가린다. 양방향 모두 `error FS0001` 이다. `type Colour = Short | Long` 뒤에 `(|Short|Standard|Extended|)` 를 정의하면 `match c with | Short -> ...` 가 FS0001, 순서를 뒤집어도 FS0001 이다.
  2. 식 자리에서는 다중 케이스의 케이스 이름을 아예 쓸 수 없다. 정의 밖에서 `let x = Short` 는 `error FS0039: 'Short' 값 또는 생성자가 정의되지 않았습니다`. 판별 유니온 케이스라면 값을 만들 수 있으니 "똑같은 방식"이 아니다.
  3. 식 자리에서 부분 액티브 패턴 이름은 동명 판별 유니온 케이스를 가리지 않는다. `type Verdict = Blank | Filled` 뒤에 `(|Blank|_|)` 를 정의해도 `let v: Verdict = Blank` 는 그대로 `Blank` 를 만든다.
  즉 정확한 규칙은 "케이스 이름은 패턴 자리(와 다중 케이스의 정의 본문)에서만 살아 있고, 그 자리 안에서는 판별 유니온 케이스와 같은 이름 공간을 쓴다"다.
  279줄을 이렇게 고쳐라.
  ```
  - 이 이름들은 패턴 자리에서만 살아 있다. 정의 밖에서 `let x = Short` 처럼 값으로 쓰려 하면 오류 FS0039 가 난다. 다만 그 패턴 자리 안에서는 판별 유니온 케이스와 같은 이름 공간을 쓴다. `Short` 케이스가 있는 판별 유니온이 이미 열려 있으면 뒤에 정의한 액티브 패턴이 그것을 가려서, 원래 판별 유니온을 매칭하던 곳에서 타입 불일치 오류 FS0001 이 난다. 순서를 뒤집어도 같다. 이름을 겹치지 않게 짓는 편이 안전하다.
  ```
  575줄을 이렇게 고쳐라.
  ```
  - 케이스 이름은 대문자로 시작해야 한다(오류 FS0623). 이 이름은 패턴 자리에서만 쓸 수 있고, 그 자리 안에서는 판별 유니온 케이스와 같은 이름 공간을 쓴다. 같은 이름이 이미 열려 있으면 나중 정의가 앞의 것을 가려 타입 불일치 오류 FS0001 을 부른다.
  ```

- [07-active-patterns.md:24, 07-active-patterns.md:14-19] "네 종류가 정확히 네 종류인 이유다"라는 논증이 성립하지 않는다. 8챕터가 이 분류에 기대므로 여기서 정리해야 한다.
  FS3872 는 "부분 × 다중 케이스" 한 칸이 없다는 것만 보여 준다. 네 종류 전체가 배타적 분류라는 근거가 되지 못한다. 실제 축은 두 개이고 매개변수는 그 위에 얹는 선택지다.
  - 축 1: 실패할 수 있는가 — 부분(이름에 `_|`) / 전체(없음)
  - 축 2: 케이스가 몇 개인가 — 하나 / 여럿
  - 얹는 것: 매개변수 — 부분과 단일 케이스에 모두 붙는다. 노트 자신이 07-active-patterns.md:566 에서 단일 케이스에 매개변수를 붙여 `(|RoundedTo|) : int -> float -> float` 를 보여 준다.
  이 격자에서 두 칸만 막혀 있다. 부분 × 다중 케이스는 문법 자체가 없고(오류 FS3872), 매개변수 × 다중 케이스는 정의는 통과하지만 사용 시점에 막힌다(오류 FS0722). "매개변수 있는 단일 케이스"는 이름이 따로 붙지 않았을 뿐 쓸 수 있다.
  네 이름은 원서와 MS 문서가 쓰는 관용 분류이지 격자에서 유도된 결과가 아니다. 24줄을 이렇게 고쳐라.
  ```
  - 네 이름은 원서와 공식 문서가 쓰는 관용 분류다. 실제 축은 두 개다. 실패할 수 있는가(이름에 `_|` 가 있는가)와 케이스가 하나인가 여럿인가다. 매개변수는 그 위에 얹는 선택지이고 부분과 단일 케이스에 모두 붙는다.
  - 이 격자에서 두 칸이 막혀 있다. 부분과 다중 케이스를 섞은 `(|Red|Black|_|)` 는 문법 자체가 없어 오류 FS3872 로 거부되고, 매개변수를 붙인 다중 케이스는 정의는 통과하지만 쓰는 순간 오류 FS0722 가 난다. 그래서 실제로 골라 쓸 조합이 네 이름에 거의 다 들어온다.
  ```
  14-19줄 표의 "매개변수 추가" 열도 손봐라. "매개변수 있는 부분" 행의 `그것이 정의다`는 매개변수가 그 종류의 전유물처럼 읽힌다. `앞쪽 매개변수를 더 받는 부분` 정도로 바꾸고, "단일 케이스" 행의 `가능` 뒤에 `(이름은 따로 없다)` 를 붙이면 격자와 이름 목록의 관계가 드러난다.

## 개선 권장

- [07-active-patterns.md:159] "`LongerThan 12.0` 은 부분 적용된 판정이고"가 용어집의 부분 적용 정의와 어긋난다. 용어집은 부분 적용을 "남은 인자를 기다리는 함수를 얻는 것"으로 못 박았는데, 패턴 자리에서는 함수 값이 만들어지지 않는다. 컴파일러가 `(|LongerThan|_|) 12.0 <검사값>` 으로 곧바로 풀어 호출한다. 2챕터에서 부분 적용을 정확히 정의했으므로 여기서 비유로 쓰면 흐려진다. 이렇게 고쳐라.
  ```
  - 시그니처를 보면 기준값이 앞, 검사 대상이 뒤다. 패턴 자리에 적은 `LongerThan 12.0` 은 컴파일러가 `(|LongerThan|_|) 12.0` 뒤에 `match` 식이 검사하는 값을 붙여 호출하는 것으로 풀린다. 그래서 검사할 값이 마지막 매개변수여야 한다.
  ```

- [07-active-patterns.md:255, 07-active-patterns.md:310] 케이스 상한이 7개인 이유를 한 줄로 붙이면 바로 위의 `Choice` 서술과 맞물려 외울 것이 하나로 줄어든다. 실측으로 `FSharp.Core` 가 내보내는 `Choice` 타입은 `FSharpChoice`2` 부터 `FSharpChoice`7` 까지 여섯 개뿐이다. 255줄 뒤에 붙일 문장.
  ```
  - 상한이 7개인 것은 `FSharp.Core` 에 `Choice<'T1,'T2>` 부터 `Choice<'T1,...,'T7>` 까지만 있기 때문이다. 담을 그릇이 없어서 생긴 한계다.
  ```

- [07-active-patterns.md:26-30] FS3872 예시 블록의 본문(`if n % 2 = 0 then Some Red else None`)이 그 자체로 타입이 맞지 않아, 독자가 오류 원인을 본문의 `Some Red` 로 오해할 수 있다. 실측으로 오류는 이름 자리(1행 6열)에서 나고 본문은 검사되지 않는다. `let (|Red|Black|_|) (n: int) = failwith "본문은 검사되지 않는다"` 로도 FS3872 만 난다. 블록 안에 주석 한 줄을 더해라.
  ```fsharp
  // 오류 FS3872: Multi-case partial active patterns are not supported.
  // 오류는 이름 자리에서 난다. 본문을 어떻게 쓰든 이 이름 형태는 성립하지 않는다.
  let (|Red|Black|_|) (n: int) =
      if n % 2 = 0 then Some Red else None
  ```

- [07-active-patterns.md:157] 패턴 조합 연산자 설명에 `|` 의 제약을 한 줄 더 붙여라. 8챕터가 값을 싣는 부분 액티브 패턴을 `|` 로 묶을 가능성이 있는데, 양쪽이 같은 변수 집합을 바인딩해야 한다는 규칙을 모르면 막힌다. 실측: `EndingWith "km" x | EndingWith "m" x` 는 통과하고, 양쪽이 다른 이름을 바인딩하면 `error FS0018: 이 'or' 패턴의 양쪽이 서로 다른 변수 집합을 바인딩합니다.` 가 난다.
  ```
  - `|` 로 묶은 두 패턴은 같은 변수 집합을 바인딩해야 한다. `EndingWith "km" x | EndingWith "m" x` 는 되지만 양쪽이 서로 다른 이름을 바인딩하면 오류 FS0018 이 난다.
  ```

- [07-active-patterns.md:284-292, 07-active-patterns.md:279] `(|Seconds|Minutes|)` 의 `Seconds` 가 같은 실행 단위의 `Track.Seconds` 필드와 이름이 같다. 실측으로 레코드 필드와 케이스 이름은 다른 이름 공간이라 실행에 문제가 없고 실제로 PASS 한다. 다만 바로 앞 불릿이 "이름을 겹치지 않게 짓는 편이 안전하다"고 말한 직후에 겹친 이름을 쓰는 예가 나와 어긋나 보인다. 케이스 이름을 `UnderMinute`/`OverMinute` 처럼 바꾸거나, 블록 뒤에 "레코드 필드와 케이스 이름은 서로 다른 이름 공간이라 겹쳐도 가려지지 않는다"는 한 줄을 넣어라.

- [07-active-patterns.md:192] 원서 pp.92-95 축약 판단은 타당하다. 액티브 패턴 관련 내용은 빠진 것이 없다. `&`/`|`, `not` 없음, 반대 패턴 정의, 가드 절 대안, 조합 폭발, 리스트 매개변수 우회로, 매개변수 있는 다중 케이스가 안 되는 이유(FS0722)까지 전부 들어 있다. 원서가 그 뒤에서 `List.map`/`List.reduce` 로 넘어가는 부분과 매핑을 매개변수로 빼는 부분은 액티브 패턴과 무관하고, `List.reduce` 는 5챕터에서 이미 다뤘으니 옮기지 않은 것이 옳다. 다만 원서를 옆에 두고 읽는 독자가 그 페이지에서 갑자기 다른 주제를 만난다. 한 줄만 덧붙이면 대조가 매끄럽다.
  ```
  - 원서는 이 실험 뒤에 액티브 패턴을 떠나 `List.map`/`List.reduce` 로 FizzBuzz 를 다시 쓰고 매핑 목록을 매개변수로 빼는 데까지 간다. 액티브 패턴 이야기가 아니고 `List.reduce` 는 5챕터에서 이미 다뤘으므로 이 노트는 옮기지 않는다.
  ```

- [07-active-patterns.md:429-441] 원서 p.98 의 튜플 반환을 판별 유니온으로 바꾼 판단은 타당하다. 원서가 스스로 권한 방향이고, 노트가 원서의 지적을 밝혀 두었으므로 대조에도 문제가 없다. 한 가지만 짚어 둔다. 원서 `(|ContainsANumber|)` 는 `bool` 을 반환하고 사용 쪽에서 `ContainsANumber false` 로 리터럴 패턴을 맞춘다. 단일 케이스의 결과에 이름을 바인딩하는 것뿐 아니라 임의의 패턴을 맞출 수 있다는 성질을 보여 주는 대목이다. 노트는 07-active-patterns.md:452 의 `Checked (Accepted q)` 중첩으로 같은 성질을 이미 보이므로 학습 공백은 없다. 보완하려면 `Checked` 블록 뒤 불릿에 "단일 케이스가 돌려준 값에는 이름 바인딩뿐 아니라 리터럴이나 판별 유니온 패턴 같은 어떤 패턴이든 맞출 수 있다" 한 줄이면 된다.

- [07-active-patterns.md:539] `risk req` 를 한 `printfn` 안에서 두 번 호출한다. 결과는 같지만 규칙 세 개를 두 번 돌린다. `let score = risk req in printfn ...` 이나 람다 안에서 미리 묶어 두면 "규칙 목록을 한 번 훑는다"는 앞 설명과 코드가 맞아떨어진다.

## 원서에 없는 최신 사항에 대한 의견

- `bool` 반환(F# 9): 넣는 것이 맞다. `if ... then Some () else None` 이 초심자가 가장 자주 걸리는 형태이고, F# 9 이후 코드에서 `bool` 판을 만나면 "부분 액티브 패턴인데 왜 `option` 이 아닌가"에서 막힌다. 지금처럼 `Some ()` 판을 주 형태로 설명하고 `bool` 판을 뒤에 대안으로 붙인 배치가 원서 대조 목적에도 맞다. 다만 위에 적은 대로 FS3868 을 함께 짚어야 `unit option` 판과의 차이가 산다.
- `[<return: Struct>]`: 초심자에게는 과하다. 힙 할당, 구조체, `voption` 세 개념이 한꺼번에 나오고 이 챕터의 목표(네 종류 구분)와 무관하다. 지우는 쪽을 권한다. 남긴다면 두 조건을 지켜라. 첫째, F# 9 가 아니라 F# 6 이후라고 정확히 적을 것. 둘째, 다섯 번째 종류가 아니라 부분 액티브 패턴의 표현만 바꾸는 것이라고 못 박을 것. 지금 주석은 둘 다 어긋난다.
- 표시 방법: 노트가 이미 쓰는 "원서는 `Some ()` 판으로 설명하고" 형태를 유지하고, 언어 버전을 문장 안에 숫자로 적어라(F# 6 이후 / F# 9 이후). "최신 F# 에서는" 같은 표현은 노트가 오래되면 틀리므로 쓰지 마라. 정리 불릿에도 같은 숫자를 적는다.

## 확인 완료

- 실측 시그니처 전부 일치. `(|PublishedYear|_|) : string -> int option`, `(|Blank|_|) : string -> unit option`, `(|Numeric|_|) : string -> bool`, `(|CallNumber|_|) : string -> int voption`, `(|LongerThan|_|) : float -> Trail -> unit option`, `(|SteeperThan|_|) : int -> Trail -> unit option`, `(|OneOf|_|) : string list -> Trail -> unit option`, `(|EndingWith|_|) : string -> string -> string option`, `(|Short|Standard|Extended|) : Track -> Choice<unit,unit,unit>`, `(|Seconds|Minutes|) : Track -> Choice<int,float>`, `(|Mon|...|Sun|) : DayOfWeek -> Choice<unit,unit,unit,unit,unit,unit,unit>`, `(|Normalized|) : string -> string`, `(|Tokens|) : string -> string list`, `(|RoundedTo|) : int -> float -> float`, `(|Succeeded|Redirected|ClientError|ServerError|) : Request -> Choice<unit,unit,unit,unit>`, `(|Segments|) : Request -> string list`.
- 다중 케이스의 반환 타입이 `Choice` 라는 서술은 정확하고 학습에 도움이 된다. 값을 싣지 않으면 자리마다 `unit`, 실으면 그 타입이 들어간다는 대비(`Choice<unit,unit,unit>` 대 `Choice<int,float>`)가 "케이스 중 하나"라는 막연한 설명보다 훨씬 낫다. 함수로 직접 호출해 보면 `Choice1Of3 ()` 이 나오므로 서술을 눈으로 확인할 수도 있다.
- 오류 코드 전부 재현. FS3872(부분 × 다중 케이스), FS0265(8케이스, 한국어 메시지 `활성 패턴은 7개가 넘는 가능성을 반환할 수 없습니다.`), FS0722(매개변수 있는 다중 케이스를 쓰는 자리, `하나의 결과를 반환하는 활성 패턴만 인수를 사용할 수 있습니다.`), FS0623(소문자 케이스 이름, `활성 패턴 케이스 식별자는 대문자로 시작해야 합니다.`), FS0025(부분 액티브 패턴만으로 구성한 `match` 식에서 `| _ ->` 를 뺀 경우). FS3872 만 영문 메시지로 나오는 것도 그대로 확인했고, 노트가 영문을 인용한 것은 맞다.
- FS0104 확인. `| _ -> Sun` 을 `| DayOfWeek.Sunday -> Sun` 으로 바꾸면 오류가 아니라 경고다. `warning FS0104: 열거형이 알려진 사례를 벗어난 값을 사용할 수 있습니다. 예를 들어, 값 'enum<DayOfWeek> (7)'은(는) 패턴에 포함되지 않은 케이스를 나타낼 수 있습니다.` 노트의 설명("열거형은 선언된 이름 밖의 값도 담을 수 있어서")이 컴파일러 메시지와 정확히 맞물린다.
- 매개변수가 단일 케이스에도 붙는다는 것 확인. `let (|RoundedTo|) (digits: int) (x: float) = Math.Round(x, digits)` 는 `int -> float -> float` 이고 `RoundedTo 2 v` 로 쓴다.
- 액티브 패턴이 그냥 함수라는 서술 확인. 네 종류 모두 바나나 클립째로 적어 일반 함수처럼 호출된다. `(|Short|Standard|Extended|) t` → `Choice1Of3 ()`, `(|Normalized|) "  AB "` → `"ab"`, `(|Numeric|_|) "12"` → `true`, `List.choose (|PublishedYear|_|)` 와 `List.filter (|Numeric|_|)` 도 통과한다.
- 패턴 조합 연산자 서술 확인. `&`, `|` 만 있고 부정이 없다. `grade` 의 출력 네 줄이 임계값 계산과 맞다(25.4km/1650m→상급, 4.6km/540m→중급, 8.2km/210m→가족 코스, 5.3km/380m→초급).
- 케이스 순서가 결과를 바꾼다는 서술 확인. `EndingWith "km"` 과 `EndingWith "m"` 의 순서, `SlowerThan 1000` 과 `SlowerThan 300` 의 순서 설명이 모두 정확하다.
- `07-query` 의 `(|Checked|) : string -> Verdict` 와 `search : string -> Result<string,string>` 가 경고 없이 빠짐없는 패턴 매칭이 된다. 가드 없는 `| Normalized q ->` 를 마지막에 두어야 한다는 설명, 단일 케이스 하나만으로 `match` 식이 완결된다는 설명 모두 맞다.
- `07-accesslog` 점수 검산 확인. `/admin/users 500 1240ms` = 40 + 20 + 10 = 70, `/admin/sessions 403 120ms` = 5 + 0 + 10 = 15. `List.sumBy` 가 `List.map` 뒤 `List.sum` 과 같다는 원서 문장을 옮긴 주석도 맞다.
- 8챕터가 이어받을 형태를 미리 확인했다. 07-active-patterns.md:412 가 예고한 "정규식 패턴 자체를 매개변수로 받는 꼴"이 실제로 성립한다. `let (|Matches|_|) (pattern: string) (input: string) = ...` 는 `string -> string -> string list option` 이고 패턴 자리에서 `Matches @"^(\d{4})-(\d{2})$" gs` 로 쓰인다. 예고를 지킬 수 있다.
- 1챕터 `(|OnActivePlan|_|)` 맛보기 참조(07-active-patterns.md:8)가 실제로 `docs/ko/01-domain-modelling.md:543` 에 있다.
