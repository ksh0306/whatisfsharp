## 2. 지시받은 세 건

### 2.1 용례 칸이 낡았다 — 04챕터 (지시대로 고쳤다. 실측 확인)

두 보고가 옳다. 04챕터 36행 한 줄에 두 낱말이 함께 들어가 있다.

```
- `dotnet test` 를 솔루션 디렉터리에서 실행하면 … 아래 인용은 `DOTNET_CLI_UI_LANGUAGE=en` 을
  붙여 얻은 영어 출력이다. CLI 메시지는 셸 로케일을 따라 번역돼 나오므로 한국어 로케일에서는
  `통과!  - 실패:     0, ...` 로 찍힌다.
```

- `CLI` — 04챕터 36행 1곳, 17챕터 8·48·120행 3곳. 용례를 `17챕터` → `4·17챕터` 로 넓혔다.
  14챕터의 `CLI` 두 곳이 `[<CLIMutable>]` 이라 용례가 아니라는 기존 비고는 그대로 남겼다.
- `locale` — 01챕터 281행, 04챕터 36행, 17챕터 48행. 용례를 `1·17챕터` → `1·4·17챕터` 로 넓혔다.
  이 행이 실측 근거로 인용해 둔 `통과!  - 실패:     0, ...` 가 04챕터 36행에 그대로 있는 문구다.

### 2.2 `exit code` 비고 확장 — 승인해 적용했다

배치 E 병합자 의견에 동의한다. 근거는 셋이다.

1. 표기("종료 코드")를 바꾸지 않으므로 앞 챕터 본문에 파급이 0 이다.
2. 배치 D 가 같은 성격의 비고 확장 4건을 "본문 파급 없음" 으로 적용한 판례가 있다.
3. 현재 비고("`main` 이 마지막에 돌려주는 `int`")가 노트의 실제 쓰임을 다 담지 못한다.
   노트에서 이 낱말이 쓰인 자리는 넷인데 둘이 `main` 반환값이 아니다.

| 챕터 | 줄 | 무엇 |
|---|---|---|
| 06 | 14 | `main` 이 돌려주는 `0` |
| 11 | 158 | 스택 오버플로로 죽은 프로세스가 `134` |
| 13 | 558 | `app.Run()` 뒤의 `0` |
| 17 | 47·94 | `dotnet new sln` 이 `73`, `dotnet sln add` 재실행이 `0` |

병합자 실측(`dotnet new sln` 두 번 → 73)과 11챕터 158행의 `134` 를 다시 확인했다. 둘 다 맞다.
배치 E 가 만들어 둔 교체행을 그대로 쓰지 않고 두 곳을 손봤다. `(병합자 실측)` 을 `(실측)` 으로
줄이고(용어집이 다른 행에서 쓰는 표기와 맞춘다), 다른 행 형식에 맞춰 용례 `6·11·13·17챕터` 를
붙였다. 인용하지 못한 `aka.ms/templating-exit-codes` 는 넣지 않았다.

적용 결과.

```
| exit code | 종료 코드 | `main` 이 마지막에 돌려주는 `int`. 0 이 성공. CLI 프로세스가 셸에 돌려주는 값도 같은 말로 부른다 — 스택 오버플로로 죽은 `dotnet fsi` 가 134(11챕터), 덮어쓰기 확인을 요구하며 멈춘 `dotnet new sln` 이 73(17챕터, 실측)이다. 컴파일러 오류 번호(`오류 FS0222`)와 성격이 다르므로 섞어 쓰지 않는다. "반환 코드" 쓰지 않음. 6·11·13·17챕터 |
```

`오류 FS0222` 를 대비로 든 것은 실제 노트에 있는 번호이기 때문이다(00·04·17챕터).
노트 수정은 따라오지 않는다. 네 자리 모두 이미 "종료 코드" 로 적혀 있다.

### 2.3 `taskResult` 의 표시 이름 — 비고에 타입 약어 표시를 넣었다

16챕터 집필자의 실측이 맞다. 병합자가 FSI 로 다시 확인했다.

```
> let a = taskResult { let! v = fetch 1
                       return v.Length }
;;
val a: TaskResult<int,DbError>

> let b = asyncResult { let! v = fetch 1
                        return v.Length }
;;
val b: Async<Result<int,DbError>>
```

왜 한쪽만 약어로 찍히는지도 확인했다. `FsToolkit.ErrorHandling` 5.2.0 에는 `TaskResult<'a,'e>`
타입 약어가 있고 `AsyncResult` 라는 타입 약어는 없다(같은 이름의 모듈만 있다).

```
> let h (x: AsyncResult<int, DbError>) = x
;;
error FS0039: The type 'AsyncResult' is not defined. Maybe you want one of the following:
   AsyncReturn
   AsyncResultOption
   AsyncResultBuilder
   AsyncResultOptionBuilder
   Async
```

`TaskResult<'a,'e>` 가 `Task<Result<'a,'e>>` 의 타입 약어라는 것은 양방향으로 확인했다 —
두 표기를 서로의 자리에 넣어도 통한다(`x: TaskResult<int,DbError> -> Task<Result<int,DbError>>`
와 그 반대 모두 컴파일된다).

넣기로 판단한 근거는 관례다. 노트는 `docs/ko/_pipeline/STYLE.md` 가 "시그니처 주석은 반드시
FSI 로 실측한 값을 적는다" 로 못박고 있고, 용어집에도 같은 상황을 다룬 판례가 셋 있다.

| 행 | 비고에 적힌 것 |
|---|---|
| `HttpFunc` | `HttpContext -> HttpFuncResult` 의 타입 약어(실측 확인) |
| `HttpFuncResult` | `Task<HttpContext option>` 의 타입 약어(실측 확인) |
| `HttpHandler` | FSI 는 약어를 펼쳐 찍기도 하고 `HttpHandler` 로 찍기도 한다 … (실측) |

`HttpHandler` 행은 "어느 쪽으로 찍히는지" 까지 적어 둔 자리다. `taskResult` 도 같은 갈래이므로
같은 형식으로 넣었다. 표기는 그대로 두었다.

노트 수정은 따라오지 않는다. 16챕터 81행이 `taskResult` 를 쓰는 자리는 산문 한 문장이고
(`Task<Result<...>>` 에는 … `taskResult` 를 쓴다) 시그니처 주석이 아니다. 실행 단위도 없다.

## 3. 용례 정정 — 지시받은 2건 밖에서 14건

그 행의 한국어 표기(그리고 표기가 원어인 행은 원어)를 해당 노트에서 찾았다. 표기가 한 번도
없는 챕터가 용례에 적혀 있으면 낡은 것으로 보았다.

## 4. 마지막 정합성 점검

### 4.1 용어집 자신의 내적 불일치 — 새로 찾은 것 1건

배치 E 가 새로 등재한 22행을 한 행씩 다시 읽었다. `do!`·`host`·`model binding` 과 같은 갈래
(한 행 안에서 어순이 갈리거나 금지한 것을 곧바로 허용하는 것)는 없었다. 확인한 자리는 이렇다.

- `loop` — "루프" 를 금지하고 `for` 루프 를 허용하지만 금지 쪽에 "단독으로" 라는 범위가
  붙어 있어 규칙이 하나로 읽힌다. `host` 를 고쳐 놓은 형태와 같다.
- `F# Software Foundation` — "재단" 으로 줄이는 것을 허용하고 "F# 소프트웨어 재단" 을 금지한다.
  두 문자열이 달라 부딪히지 않는다. 16챕터 43·44·45행이 규칙대로 "재단" 을 쓴다.
- `Microsoft Learn` — "MS ko" 를 용어집 안에서만 쓰는 약칭으로 못박았다. 노트 18개에 0회다.
- `resource (learning material)`·`master page`·`payload` — 예외의 범위를 먼저 적고 그 밖을
  금지한 형태여서 규칙이 하나로 읽힌다(배치 D·E 가 확인한 것과 같다).

새로 찾은 것 1건.

- `store` 행이 00 노트를 `서문·6·11챕터` 로 적고 있었다. 배치 E 가 같은 배치에서 확정한 형태는
  `서문 챕터` 이고, 다른 네 행(`command palette`·`keyboard shortcut`·`F# Software Foundation`·
  `preface`)은 모두 `서문 챕터·…` 로 적는다. `store` 한 행만 "챕터" 가 빠져 있었다.
  → `서문 챕터·6·11챕터` 로 고쳤다. 이제 용어집 안의 00 노트 지칭이 5곳 모두 같은 형태다.

### 4.2 두 행에 걸친 모순 — 0건. 대신 행-노트 모순 2건을 찾았다

`header (HTTP)`/`header row` 갈래(두 행이 같은 낱말에 정반대 규칙을 세우는 것)는 없었다.
355행에서 금지 표기로 인용된 문자열을 전부 뽑아 다른 행의 확정 표기와 맞대어 보았고 충돌 0건이다.
`header row`(헤더 줄)는 앞 정리에서 나온 노트 수정 4곳이 적용돼 있어 지금은 06·11챕터가 쓰는
살아 있는 표기다.

그 대신 같은 갈래의 모순이 행과 노트 사이에서 둘 나왔다. 둘 다 예외의 범위를 비고에 적어
해소했다. 표기는 건드리지 않았다. 판례는 배치 E 가 `store` 행에 04챕터의 "리포지터리" 한 곳을
예외로 적어 둔 처리다.

- `Map` (collection type) — 행이 "사전" 을 금지하는데 14챕터가 `ConcurrentDictionary` 를
  여섯 곳에서 "사전" 이라 부르고 16챕터도 한 곳에서 그렇게 부른다. 14챕터는 같은 문서 369행에서
  `Map` 도 한 번 언급하므로 한 챕터 안에서 두 개념이 부딪히는 자리다. 금지의 대상이 이 컬렉션의
  역어라는 범위를 적었다.
- `next steps` — 행이 "다음 단계" 를 금지하는데 03챕터 370행("다음 단계는 이 익명 함수를
  이름 있는 함수로 빼내는 것")과 09챕터 107행("다음 단계에서 쓴다")이 절차의 바로 다음 차례를
  가리키는 일반 명사로 쓴다. 절 제목과 방향 안내에 걸리는 규칙이라는 범위를 적었다.

두 건 모두 되돌리려면 비고에서 예외 문장을 빼고 노트 9곳(14챕터 6, 16챕터 1, 03챕터 1,
09챕터 1)을 고치는 쪽이 된다. 그 판단이 필요하면 사람이 정할 자리다. 병합자는 노트 쪽 쓰임이
둘 다 다른 개념을 가리킨다고 보아 예외 쪽을 택했다.

### 4.3 죽은 항목 — 확정 표기가 18개 노트에 한 번도 없는 행 7개

한국어 표기(원어 표기 행은 원어)를 18개 노트 전체에서 찾아 0회인 행을 뽑았다.

| 행 | 표기 | 처리 |
|---|---|---|
| `abstract member` | 추상 멤버 | 그대로 둔다. 행이 "키워드를 가리킬 때는 `abstract member` 를 백틱으로 쓴다" 로 정하고 10챕터가 그대로 따른다. 죽은 것이 아니다 |
| `downcast` | 하향 변환 | 그대로 둔다. 행이 이미 "`:?>` 는 아직 어느 노트에도 나오지 않는다 — 짝 낱말이 갈리지 않게 미리 등재했다" 로 밝혀 두었다 |
| `package reference` | 패키지 참조 | 비고를 고쳤다. 용례가 `4·17챕터` 라 사실과 어긋났다. 두 챕터가 명령(`dotnet add package`)과 `.fsproj` 항목(`PackageReference`)으로만 쓴다는 사실을 적고 `payload` 행 판례를 가리켰다 |
| `payload` | 페이로드 | 그대로 둔다. 행이 이미 "13·14챕터는 식별자로만 쓰고 있다" 와 등재 이유를 밝혀 두었다 |
| `struct representation` | 구조체 표현 | 그대로 둔다. FSI 한국어 메시지 표기를 받아 적은 행이고 용례를 달지 않았다. 07챕터 106행이 "이 노트는 다루지 않는다" 로 명시한다 |
| `type test operator` | 타입 테스트 연산자 | 그대로 둔다. 용례가 없다. 노트가 쓰는 것은 짝 행 `type test pattern`(타입 테스트 패턴, 03·10·14챕터)이고, 이 행은 "식 위치의 `x :? T`" 를 패턴과 갈라 두는 자리다 |
| `web framework` | 웹 프레임워크 | 비고를 고쳤다. 용례가 `13챕터` 라 사실과 어긋났다. 13챕터가 Giraffe 를 무엇으로 소개하는지 적고 등재만 해 둔다는 것을 밝혔다 |

행을 지우지 않은 이유는 셋이다. 확정 표기를 건드리지 않는 것이 이 작업의 전제이고, 일곱 행이
모두 짝 낱말이 갈리는 것을 막는 자리이며(하향/상향 변환, 패턴/연산자, 패키지/프로젝트 참조),
`header row` 때와 달리 노트를 고쳐 표기를 살릴 실익이 없다 — 남은 챕터가 없다.

### 4.4 배치 E 3.2 (`assignment operator`) — 적용하지 않았다

배치 E 가 "16-1 을 적용하면 이 행의 용례도 `1·13챕터` 로 넓히는 편이 앞뒤가 맞는다" 로 남긴
항목이다. 조건은 충족됐다(16챕터 39행이 "가변 바인딩은 1챕터가 `<-` 와 함께 처음 다루고" 로
바뀌어 있다). 그래도 넓히지 않았다. 근거는 실측이다.

- 표기 "할당 연산자" 는 13챕터 232·241·683행과 14챕터 162행에만 있다. 01챕터에는 0회다.
- 01챕터 178·181·184·608행이 `<-` 를 다루기는 하지만 그 동작을 "대입" 이라 적는다.

용례 칸은 표기가 쓰인 자리를 적는 칸이므로 여기에 01챕터를 넣으면 3절에서 고친 14건과 같은
종류의 어긋남이 하나 새로 생긴다. `<-` 가 처음 나오는 자리를 알려 주려면 용례가 아니라 비고
본문에 적을 일이고, 그것은 표기 규칙과 무관한 색인이다.

다만 실측 과정에서 딸린 사실 하나를 남긴다. 01챕터는 `<-` 의 동작을 "대입" 으로, 13·14챕터는
"할당" 으로 적는다. 이 행이 금지한 것은 "대입 연산자" 라는 온낱말이므로 01챕터가 규칙을 어긴
것은 아니다. 한 낱말로 통일하려면 표기를 건드리는 일이 되어 `[기확정 변경 제안]` 이 필요하다.
병합자는 제안하지 않는다 — 01챕터의 "대입" 은 `=`(바인딩·비교)와 대비시키는 자리에서만 쓰이고
연산자의 이름으로 쓰이지 않아 실제로 헷갈릴 자리가 없다.
