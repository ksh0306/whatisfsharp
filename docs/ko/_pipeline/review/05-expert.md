## 수정 필요 (기술 오류)

### 1. [05-collections.md:27, 32-33] 값 제한 서술이 사실과 다르다

현재 서술: "빈 리스트 `[]` 는 원소 타입을 알 수 없으므로 그대로 `let` 에 묶으면 값 제한(value restriction) 오류가 난다."

실측하면 오류가 나지 않는다. `[]` 는 인자 없는 유니온 케이스이므로 자동 일반화 대상이고 `'a list` 로 일반화된다.

```
> let noLaps = [];;
val noLaps: 'a list          // 오류도 경고도 없다
```

`List.empty`, `Set.empty`, `Array.empty`, `None` 도 모두 같다. 값 제한 FS0030 이 나는 것은
함수 적용 결과나 가변 위치를 이름에 묶을 때다.

```
> let reversed = List.rev [];;
error FS0030: 값 제한: 값 'reversed'에 유추된 제네릭 형식이 있습니다.
    val reversed: '_a list
> let mutable pending = [];;     // 같은 FS0030
```

FS0030 메시지 자체가 해결책으로 "정수 리터럴, 문자열 리터럴 또는 공용 구조체 대/소문자와 같은 간단한
데이터 용어로 정의합니다" 를 제시한다. 즉 `[]` 는 컴파일러가 일반화해 주는 쪽에 속한다.
지금 서술은 값 제한이 무엇 때문에 나는지를 반대로 가르친다.

고칠 것 — 27줄 불릿을 이렇게 바꾼다.

```
- 빈 리스트 `[]` 는 원소 타입이 정해지지 않아 자동 일반화(auto-generalization)로 `'a list` 이 된다. 특정 타입으로 못박아야 하면 타입 주석을 붙인다.
- 같은 빈 리스트라도 `let reversed = List.rev []` 처럼 함수를 적용한 결과를 이름에 묶으면 일반화가 막혀 값 제한(value restriction) 오류 FS0030 이 난다. 매개변수 없는 `let` 이 제네릭이 될 수 없다는 규칙이고, 타입 주석을 붙이거나 쓰이는 문맥에서 타입이 정해지게 하면 풀린다.
```

32-33줄 코드 주석도 이유가 바뀌므로 함께 고친다. 바인딩 자체는 그대로 두어도 된다.

```fsharp
// 주석이 없으면 'a list 로 일반화된다. int 로 못박으려면 타입 주석을 붙인다
let noLaps : int list = []
```

값 제한의 실제 예를 보이고 싶으면 아래 조각을 `id` 없는 블록으로 넣는 것이 정확하다(실측한 오류다).

```fsharp
// 오류 FS0030: 값 제한. 값 'reversed'에 유추된 제네릭 형식이 있습니다.
//              val reversed: '_a list
let reversed = List.rev []
```

### 2. [05-collections.md:166, 630] `~By` 계열을 하나의 규칙으로 묶은 것이 틀렸다

현재 서술(166줄): "같은 모양의 짝이 여러 개 있다. `List.averageBy`, `List.maxBy`, `List.minBy`,
`List.countBy` 도 모두 '함수로 뽑아낸 값을 기준으로 집계한다'는 규칙을 따른다."
그리고 630줄: "`map` 뒤에 `sum` 을 붙이는 모양은 `sumBy` 하나로 줄어든다. `averageBy`, `maxBy`,
`minBy`, `countBy` 도 같은 규칙을 따른다."

`map` + 집계 = `~By` 라는 등식은 `sumBy`/`averageBy` 에만 성립한다. `maxBy`/`minBy` 는 뽑아낸 값이
아니라 원소를 돌려주고, `countBy` 는 `('b * int) list` 를 돌려준다. `List.count` 라는 짝도 없다.

```
> [("a",3);("b",5);("c",1)] |> List.maxBy snd;;
val it: string * int = ("b", 5)
> [("a",3);("b",5);("c",1)] |> List.map snd |> List.max;;
val it: int = 5
```

같은 노트가 140줄에서 `List.distinctBy` 를 두고 "돌려주는 것은 키가 아니라 원래 원소"라고 굳이 짚어
두었으므로, `maxBy`/`minBy` 를 `sumBy` 와 한 줄에 묶는 것은 챕터 안에서 서로 어긋나기도 한다.

고칠 것 — 166줄을 이렇게 바꾼다.

```
같은 이름 규칙을 따르는 함수가 여럿 있지만 돌려주는 것이 제각각이다. `List.averageBy` 는 `sumBy` 처럼 뽑아낸 값을 집계해 값 하나를 내놓고, `List.maxBy` 와 `List.minBy` 는 뽑아낸 값을 기준으로 고른 원소를 그대로 돌려주며, `List.countBy` 는 `(키 * 개수)` 튜플의 리스트를 돌려준다. 뒤의 셋은 `map` 뒤에 집계 함수를 붙인 것과 결과 타입이 다르므로 쓰기 전에 시그니처를 본다. 그리고 `List.average` 와 `List.averageBy` 에는 함정이 하나 더 있다.
```

630줄 요약 불릿도 함께 바꾼다.

```
- `map` 뒤에 `sum` 을 붙이는 모양은 `sumBy` 하나로 줄어들고 `averageBy` 도 같다. 다만 `maxBy`/`minBy` 는 뽑아낸 값이 아니라 원소를 돌려주고 `countBy` 는 `(키 * 개수)` 리스트를 돌려주므로 결과 타입이 다르다.
```

## 개선 권장

### [05-collections.md:116] `List.sum` 시그니처 주석만 실측 표기가 아니다

157-158줄의 `sumBy`, 169-172줄의 `averageBy` 는 `^b` 와 제약 전문을 실측대로 적었는데
116줄만 `'a` 와 줄인 제약으로 적혀 있어 계열이 어긋난다. FSI 실측은 이렇다.

```
val inline s1: xs: ^a list -> ^a
    when ^a: (static member (+) : ^a * ^a -> ^a) and ^a: (static member Zero: ^a)
```

```fsharp
// List.sum : ^a list -> ^a
//   (when ^a : (static member (+) : ^a * ^a -> ^a) and ^a : (static member Zero : ^a))
```

### [05-collections.md:180-181, 185] 오류 메시지와 `DivideByInt` 서술을 실측 문구에 맞춘다

FSI 실제 메시지는 "필수(실제 또는 기본 제공) 멤버 'DivideByInt'" 다. 노트는 "필수 멤버" 로 줄였는데,
빠진 "(실제 또는 기본 제공)" 이 바로 185줄의 "`float`, `decimal`, `float32` 에는 `DivideByInt` 가
있으므로" 를 정확하게 만들어 준다. `System.Double` 에 그런 정적 멤버가 실제로 있는 것이 아니라
컴파일러가 기본 제공하는 것이다. 두 곳을 함께 손대는 편이 좋다.

```fsharp
// 오류 FS0001: 'int' 형식에는 필수(실제 또는 기본 제공) 멤버 'DivideByInt'이(가) 없기 때문에
//              'List.average'이(가) 이 형식을 지원하지 않습니다.
[1; 2; 3] |> List.average
```

185줄은 "`float`, `decimal`, `float32` 에는 컴파일러가 `DivideByInt` 를 기본 제공하므로" 로 고친다.
세 타입 모두 실측했다: `[1;2;3] |> List.averageBy float` = `2.0`,
`... averageBy decimal` = `2M`, `... averageBy float32` = `2.0f`.

### [05-collections.md:86] `%A` 서술을 한 걸음 더 정확하게

`%A` 는 F# 의 구조 출력기를 쓰지만, 구조를 모르는 .NET 타입에서는 `ToString()` 결과로 떨어진다.
실측하면 `printfn "%A" (Custom())` 이 `Custom.ToString()` 값을 그대로 낸다. 원서(p.65 상자글)가
"%A formats the output using the types toString() method" 라고 적은 것이 부정확한 지점이므로,
정정하는 노트라는 것을 드러내면 대조 독자에게 도움이 된다.

```
`%A` 는 F# 의 구조 출력기를 쓴다. 리스트나 레코드를 사람이 읽을 수 있게 펼쳐 주고, 구조를 모르는 .NET 타입에서는 `ToString()` 결과로 떨어진다. 원서가 `%A` 를 "`ToString()` 을 쓴다"고 적은 것은 이 뒷부분만 말한 것이다.
```

### [05-collections.md:24] "원소 하나짜리 튜플 리스트" 가 두 가지로 읽힌다

`[2, 5, 3]` 은 `(int * int * int) list` 이고 원소가 튜플 하나뿐인 리스트다. 실측 결과는 `[(2, 5, 3)]` 이다.
"튜플 하나만 담은 리스트가 된다(`[2, 5, 3]` 은 `(int * int * int) list`)" 처럼 결과 타입을 적어 두면
오독이 없다.

### [05-collections.md:152] `int * decimal` 이 곱셈인지 튜플 타입인지 갈린다

바로 앞 137·143줄에서 `(int * decimal)` 을 튜플 타입으로 쓴 뒤라 같은 표기를 곱셈 뜻으로 다시 쓰면
읽는 쪽이 멈춘다. "`int` 값과 `decimal` 값을 곧바로 곱하는 것 같은 암묵적 변환을 허용하지 않는다" 로
풀어 쓰는 것이 낫다.

### [05-collections.md:273] "절대 실패하지 않는다" 는 과한 단정

`fold` 는 빈 리스트에서 초기값을 그대로 돌려주지만, `folder` 가 예외를 던지면 `fold` 도 실패한다.
"반면 `fold` 는 초기값이 있으므로 빈 리스트에서도 그 초기값을 돌려주고 이 이유로는 실패하지 않는다" 정도로
범위를 좁힌다.

### [05-collections.md:411, 633] `reduce` 에 넘기는 함수를 `folder` 라고 부르지 않는다

FSharp.Core 의 매개변수 이름은 `List.fold` 가 `folder`, `List.reduce` 가 `reduction` 이다.
공식 문서를 찾아볼 독자를 위해 411줄은 "첫 원소가 이 함수를 거치지 않고 그대로 초기 상태가 된다",
633줄은 "첫 원소가 함수를 거치지 않는다" 로 적는 편이 정확하다.

### [05-collections.md:279 앞뒤] 원서 p.69-70 의 출력 주석이 실제와 다르다는 것을 한 줄로 남길 만하다

원서는 `myList = [1;2;3;4;5;7;6;5;4;3]` 에 `List.groupBy id` 를 걸고 결과를
`[(1,[1]);(2,[2]);(3,[3;3]);(4,[4;4]);(5,[5;5]);(6,[6]);(7,[7])]`, 이어지는 `unique` 를
`[1;2;3;4;5;6;7]` 이라고 적었다. 실제로는 처음 나타난 순서가 유지되므로 둘 다 다르다.

```
> [1;2;3;4;5;7;6;5;4;3] |> List.groupBy id;;
val it: (int * int list) list =
  [(1, [1]); (2, [2]); (3, [3; 3]); (4, [4; 4]); (5, [5; 5]); (7, [7]); (6, [6])]
> [1;2;3;4;5;7;6;5;4;3] |> List.groupBy id |> List.map fst;;
val it: int list = [1; 2; 3; 4; 5; 7; 6]
```

314줄이 "처음 나타난 순서를 지킨다" 를 이미 정확히 적어 두었으므로, 그 문장 뒤에
"원서 p.69-70 의 결과 주석은 정렬된 순서로 적혀 있으나 실제 결과는 입력에서 처음 나타난 순서다" 를
한 문장 붙이면 원서를 옆에 두고 읽는 독자가 자기 실행 결과를 의심하지 않는다.
`Set` 만 정렬 순서로 재배치된다는 314줄의 설명과도 잘 맞물린다.

같은 자리에 원서의 지시가 어긋나는 것도 한 줄로 적어 둘 만하다. 원서 p.71 은 테스트 파일

### [05-collections.md:196-197, 209-211] 캐럿 표시가 두 번째부터 어긋난다

한글 라벨이 두 칸 폭이라 `^folder(상태,원소)` 뒤의 `^초기값`·`^입력`·`^결과` 가 가리키려는 위치보다
오른쪽으로 밀린다(등폭 글꼴 기준 3~4칸). 첫 캐럿만 남기고 나머지는 다음 줄 산문으로 옮기거나,
라벨을 캐럿 줄 대신 별도 주석 목록으로 적는 편이 읽힌다. 시그니처 자체는 정확하므로 표시 방식만의 문제다.

### 범위 판단 — `Array`·`Seq` 절제는 지금이 적절하다

원서는 p.63 에서 이 챕터를 `List` 로 한정하고 컴프리헨션 문단(p.65)에서만
"Seq 와 Array 에도 있지만 이 챕터에서는 쓰지 않는다" 고 덧붙인다. 노트의 처리(성격 차이 세 불릿 +
`ResizeArray<'T>` 문단 + 135줄 `Seq.map` 1회)는 이 범위를 정확히 지키고 있고, 빠진 것으로 느껴지는
대목은 없다. 지연 평가를 여기서 더 파는 것은 반대한다. 6챕터가 "시퀀스를 `try/with` 로 감싸면 예외를
놓친다" 는 실패 사례로 지연 평가를 본론으로 다루므로, 그 자리에서 처음 놀라는 편이 학습에 낫다.

다만 두 곳만 한 절씩 보태는 것을 권한다.

1. 135줄 끝. "지연 평가가 필요하면 `Seq.map` 을 쓰면 된다" 뒤에
   "시퀀스는 순회할 때마다 다시 계산되므로 주의할 점이 있고, 자세한 것은 6챕터에서 다룬다" 를 붙인다.
   지금 문장만 읽고 `List` 파이프라인을 `Seq` 로 바꿔 두면 재계산에 걸린다.
2. 26줄 컴프리헨션 불릿 끝. 원서 p.65 대로 "같은 문법이 `Seq` 와 `Array` 에도 있다" 를 반 문장 넣는다.
   이 챕터에서 쓰지는 않는다는 것도 함께 적으면 범위가 흐려지지 않는다.

## 확인 완료

집필자가 실측으로 예상을 뒤집었다고 보고한 항목은 전부 재확인했고 전부 맞다.

- `List.concat : 'a list seq -> 'a list` — 실측 `val a: ('a list seq -> 'a list)`.
  바깥이 `seq` 라는 서술도 맞다. `List.concat [| [1;2]; [3] |]` 과 `List.concat (seq { [1]; [2] })`
  모두 컴파일된다.
- `List.distinctBy : ('a -> 'b) -> 'a list -> 'a list  (when 'b : equality)` — 실측 일치.
  143-144줄이 "결과 타입이 `'b list` 가 아니라 `'a list` 다" 를 짚은 것도 정확하다.
- `List.sumBy`/`List.averageBy` 는 SRTP 라서 `let f = List.sumBy` 로 시그니처를 잴 수 없다.
  실측하면 `List.sum` 도 같은 FS0071(`obj` 에 `op_Addition` 없음)이 난다. `let inline` 으로 감싸
  측정한 157-158·169-172줄 주석은 제약 순서까지 FSI 출력과 같다.
- `[1; 2; 3] |> List.average` 는 FS0001 이다. `averageBy id` 도 같은 FS0001 이다.
- `List.tryReduce` 는 없고 FS0039 다. FSI 가 대안으로 `tryItem`, `reduce` 를 제시한다.
- `Set` 처리가 이 챕터에서 가장 잘된 부분이다. 원서는 `setResult` 를 입력 순서와 무관하게 정렬된
  `[1..7]` 로 적어 두어 `Set` 이 순서를 보존하는 것처럼 오해하게 만드는데(정수 예제라 차이가
  안 드러난다), 노트는 한글 문자열로 바꿔 `set ["경로"; "일반"; "학생"]` 이 나오는 것을 보이고
  `equality`/`comparison` 제약 차이까지 붙였다. 실행 결과도 주석과 일치한다.
  참고로 F# 의 문자열 비교는 서수 비교이므로 재배치 기준은 UTF-16 코드 단위다
  (경 U+ACBD < 일 U+C77C < 학 U+D559). 노트가 "값의 비교 순서" 라고만 적어 과한 주장을 하지 않은 것도 맞다.

`fold` 계열은 다음을 확인했다.

- `List.fold : ('a -> 'b -> 'a) -> 'a -> 'b list -> 'a`. `folder` 의 첫 매개변수가 상태, 둘째가 원소라는
  205줄 서술과 196-197줄 주석이 실측과 일치한다.
- `List.foldBack : ('a -> 'b -> 'b) -> 'a list -> 'b -> 'b`. 매개변수 순서(원소, 상태)와 인자 순서
  (`folder`→리스트→초기값)가 양쪽 다 뒤집힌다는 보고가 맞다. 222줄의 세 가지 차이 정리(방향·매개변수
  순서·인자 순서)가 정확하고, `foldBack` 을 파이프 끝에 두기 어렵다는 설명도 시그니처에서 그대로 나온다.
- 210-219줄의 `v :: acc` 대조 예제가 방향 차이를 정확히 드러낸다. 실행 결과 `[3; 2; 1]` / `[1; 2; 3]`.
- `List.reduce : ('a -> 'a -> 'a) -> 'a list -> 'a`. 상태와 원소의 타입이 같아야 한다는 설명이 맞다.
- 빈 리스트에서 `ArgumentException` 이다. FSharp.Core 구현이
  `match list with [] -> invalidArg ... | h::t -> fold reduction h t` 이므로 예외 타입도, 첫 원소가
  함수를 거치지 않고 초기 상태가 된다는 설명도 구현과 그대로 맞다.
- "여러 풀이" 절의 `reduce` 오답 설명이 정확하다. `usage = [40; 120; 95; 260; 100; 175]` 에서
  올바른 답은 20+160+75 = 255 이고 `reduce` 는 초기 상태 40 에서 시작해 295 를 낸다. 차이가 정확히
  첫 원소 40 이므로 "첫 원소 40 이 그대로 더해졌다" 는 주석이 맞다. 여섯 가지 풀이 모두 실행해
  255/255/255/255/295/255 를 확인했다.

그 밖에 확인한 것.

- 절 페이지 경계는 집필자 실측이 맞다. 원문의 첫 페이지 표지가 `5 - Introduction to Collections 64` 이고
  그것이 `let items = []` 바로 앞에 오므로, 챕터 제목·Before We Start·The Basics·Core Functionality
  제목까지가 p.63 안이다. 대조 표(643-650줄)의 페이지 배정도 원문 표지 위치와 전부 맞다.
- `::` 가 `|>` 보다 강하게 묶인다(480줄). `1 :: [2;3] |> List.length` = 3.
- `List.countBy (fun t -> t.Tier)` 가 `groupBy` + `List.length` 조합과 같은 결과·같은 순서를 낸다(338줄).
  실측 `[("일반", 2); ("학생", 1); ("경로", 1)]`.
- `List.groupBy`/`List.distinct` 가 처음 나타난 순서를 지킨다(314줄).
- 쉼표 리터럴 `[2, 5, 3]` 이 `[(2, 5, 3)]` 이다(24줄의 주의가 맞다).
- 86줄의 보간 서식 설명대로 `$"%A{rest}"` 가 동작한다.
- 실전 예제의 `reduceBean` 이 음수 항목을 넣고 `recalculate` 후 `Grams > 0` 으로 걸러 내는 방식으로
  전량 차감·없는 원두·빈 배합표 세 경계를 한 번에 처리한다(505줄 설명이 정확하다).
  12개 비교 검사 전부 OK 이고 마지막 "원본 불변" 검사가 불변성의 요점을 그대로 보인다.
- `id` 배정이 옳다. `id` 없는 세 블록은 각각 이유가 분명하다. 179-183줄은 실제로 FS0001 이 나는
  오류 예시이고(오류 코드도 맞다), 453-457줄의 미완성 `addPortion` 은 `id` 를 붙이면 뒤의 완성판을
  가려 오해를 만들며, 522-538줄의 xUnit 블록은 참조가 없어 FSI 에서 실행할 수 없다.
  반대로 `id` 가 붙은 블록 중 컴파일되지 않는 것은 없다.
- float 결과 주석이 실제 출력과 일치한다(`[8.4; 4.9; 14.0; 2.1; 10.5; 6.3]`). `20.0 * 0.7` 같은
  이진 부동소수 오차가 표시로 새지 않는지 따로 확인했다.
