# 14챕터 용어 후보 (F# 전문가 검수, 후보 모드)

검수 대상: `docs/ko/14-api-with-giraffe.md`
`docs/ko/GLOSSARY.md` 는 읽기만 했다. 편집하지 않았다(13·15챕터 전문가와 동시 작업 중).

지금 용어집(275행)에는 웹·Giraffe 계열 용어가 한 항목도 없다. 13챕터 후보 파일도 아직 없으므로
`라우팅`·`미들웨어`·`핸들러`·`엔드포인트`·`요청`/`응답`·`직렬화기` 같은 13챕터가 먼저 쓴 낱말은
아래 3절에 근거만 남기고 표에는 넣지 않았다. 병합 담당자가 13챕터 후보와 함께 정하면 된다.

## 1. 확정 제안 (14챕터가 새로 쓰는 낱말)

| 영어 | 한국어 표기 | 비고 |
|---|---|---|
| content negotiation | 콘텐츠 협상 | 클라이언트가 `Accept` 헤더로 원하는 형식을 말하고 서버가 규칙에 있는 것을 골라 응답하는 방식. Giraffe 는 `negotiate` 핸들러가 판단한다. 집필자가 쓴 "내용 협상" 대신 "콘텐츠 협상"을 택한다 — MS Learn ko(ASP.NET Core 응답 형식 지정)와 MDN ko 가 둘 다 "콘텐츠 협상"이고, 15챕터가 `content root` 를 이미 "콘텐츠 루트"로 쓰고 있어(15챕터 38·541·684줄) 같은 문서군 안에서 web 문맥의 `content` 를 두 갈래로 옮기게 된다. "내용 협상"·"컨텐츠 협상" 쓰지 않는다. 14챕터 본론 |
| DTO | DTO | Data Transfer Object 의 약어. 첫 등장만 `DTO(Data Transfer Object)` 로 병기하고 이후 약어만 쓴다. 번역하지 않는다 — "데이터 전송 객체"는 통용되지만 코드에 남는 이름이 아니고, 이 노트가 `object`→객체 를 쓰지 않는다. 도메인 타입과 별개로 요청·응답 경계에만 쓰는 평평한 타입을 가리킨다. 14챕터 본론 |
| indexer | 인덱서 | `dict[key]` 형태로 읽고 쓰는 멤버. MS ko 표기와 일치. 14챕터가 `ConcurrentDictionary` 를 다루며 "인덱서 설정"(쓰기)과 "인덱서로 읽기"를 갈라 쓴다 — 전자는 추가·갱신을 겸하고 후자는 없는 키에서 `KeyNotFoundException` 을 던지므로 두 방향을 한 낱말로 뭉개지 않는다. "색인기"·"인덱서 접근자" 쓰지 않는다. 14챕터 본론 |
| model binding | 모델 바인딩 | 요청 본문·쿼리 문자열 같은 바깥 데이터를 타입 있는 값으로 되돌리는 일. Giraffe 에서는 `ctx.BindJsonAsync<'T>()`. MS ko 표기와 일치. 검증과 구별해 쓴다 — 바인딩은 빠진 필드를 타입의 기본값으로 채우므로 `string` 필드에 `null` 이 들어온다(14챕터 실측). "모델 결합"·"바인딩" 단독 쓰지 않는다. 14챕터 본론 |
| `out` parameter | `out` 매개변수 | `bool TryGetValue(TKey, out TValue)` 처럼 결과를 인자 자리로 돌려주는 .NET 관례. 키워드는 백틱으로 원어를 쓰고 뒤에 "매개변수"를 붙인다. MS ko 는 "out 매개 변수"이나 이 노트는 `parameter`→매개변수 확정 표기를 따라 붙여 쓴다. F# 은 이런 메서드를 `bool * 'Value` 튜플을 돌려주는 함수로 보므로 패턴 매칭 한 번에 갈라낼 수 있다. "출력 매개변수" 쓰지 않는다. 14챕터 본론 |
| payload | 페이로드 | 응답이나 요청 본문에 싣는 데이터 덩어리. 음차 고정. MS ko·커뮤니티가 함께 쓴다. 13·14챕터가 식별자로만 쓰고 있고(`payload`, `toPayload`) 산문에는 아직 한 번도 등장하지 않는다 — 등재 이유는 앞으로 산문에 쓸 때 "적재물"·"실은 값" 같은 갈래가 생기는 것을 막으려는 것이다. 표기가 필요 없으면 "응답 본문"으로 풀어 쓰는 것도 허용한다 |
| route template | 경로 템플릿 | ASP.NET Core 라우팅이 읽는 경로 패턴 문자열. `routef "/%O"` 는 `/{O0:regex(...)}` 라는 경로 템플릿으로 번역된다. MS ko 표기와 일치. "라우트 템플릿"·"경로 서식" 쓰지 않는다. 14챕터 본론 |
| service location | 서비스 로케이션 | 의존성을 매개변수로 받지 않고 필요할 때 컨테이너에 물어보는 방식(`ctx.GetService<'T>()`). 원서 p.182 표기가 service location 이므로 그것을 음차한다. 패턴 이름으로는 "서비스 로케이터(Service Locator)"가 더 널리 쓰이니, 패턴 자체를 가리킬 때만 그 이름을 쓰고 이 노트 본문은 "서비스 로케이션"으로 통일한다. "서비스 위치 지정" 쓰지 않는다. 14챕터 본론 |
| singleton | 싱글턴 | 의존성 주입 컨테이너에 인스턴스 하나만 두고 앱 전체가 공유하게 등록하는 수명(`AddSingleton`). 외래어 표기법대로 "싱글턴"이며, 이 노트가 이미 `overflow`→"오버플로"에서 같은 원칙을 택했다. MS ko 문서에는 "싱글톤"과 원어 "Singleton"이 섞여 나오지만 규범 표기를 따른다. "싱글톤"·"단일체" 쓰지 않는다. 14·15챕터 |
| status code | 상태 코드 | HTTP 응답의 세 자리 숫자. MS ko·MDN ko 표기와 일치. 13·14챕터가 병기 없이 쓰고 있어 표기를 확정만 하는 것이다. 노트는 숫자와 이름을 함께 적을 때 `Successful.CREATED`(201) 처럼 괄호에 숫자를 넣는다. "응답 코드"·"HTTP 코드" 쓰지 않는다 |

## 2. 기확정 행 비고 보강 제안 (표기는 그대로)

| 영어 | 한국어 표기 | 비고 |
|---|---|---|
| pipeline | 파이프라인 | [기확정 변경 제안] 표기는 그대로 두고 비고에 한 문장을 덧붙인다 — "웹 문맥의 request pipeline·middleware pipeline 에는 이 낱말을 쓰지 않는다. 13-15챕터는 미들웨어 순서를 '요청이 지나는 길'로 풀어 쓴다." 근거: 지금 비고가 `\|>` 로 값을 흘려보낸 코드 형태로만 한정하고 있어 13·14챕터에서 "파이프라인"이 두 뜻으로 갈릴 여지가 있고, 실제로 세 챕터 모두 이 낱말을 웹 문맥에 한 번도 쓰지 않았다(집필자 판단이 옳다). 비고만 고치는 변경이라 앞 챕터 본문 파급은 없다 |
| overload | 오버로드 | 12챕터 후보 파일이 같은 행을 올렸다. 중복 등재하지 말고 12챕터 표기를 그대로 쓰면 된다. 14챕터가 실측으로 보강할 것이 하나 있다 — `ConcurrentDictionary.TryRemove` 는 오버로드가 둘(`TryRemove(key, out value)` 와 `TryRemove(KeyValuePair)`)이라 키 타입 주석이 없으면 `bool` 만 돌려주는 쪽이 잡혀 패턴 매칭에서 `error FS0001` 이 난다. 12챕터 행의 "오버로드 해결" 용법 그대로다 |

## 3. 13챕터와 공통 — 13챕터 후보와 함께 정할 것 (표에 넣지 않음)

14챕터는 아래 낱말을 13챕터 본문 표기 그대로 썼다. 13챕터 전문가가 동시에 확정하고 있어
결론이 갈릴 수 있으므로 여기서는 근거만 남긴다. 병합 때 13챕터 표기를 따르면 14챕터는
손댈 것이 없다.

- `routing`→라우팅, `endpoint routing`→엔드포인트 라우팅, `endpoint`→엔드포인트,
  `handler`→핸들러, `middleware`→미들웨어, `request`/`response`→요청/응답,
  `request body`/`response body`→요청 본문/응답 본문, `dependency injection`→의존성 주입,
  `anonymous record`→익명 레코드, `serializer`→직렬화기, `serialization`→직렬화,
  `deserialization`→역직렬화, `header`→헤더, `container`→컨테이너.
- 이 가운데 `deserialization`→역직렬화 는 13챕터가 직렬화 방향만 다루므로 14챕터에서
  처음 쓰인다(237·299·362·910줄). 13챕터 후보에 없으면 병합 때 이 항목만 따로 넣으면 된다.
- `content root`→콘텐츠 루트 는 15챕터가 쓴다. 1절의 `content negotiation` 표기 근거가
  그 항목과 맞물리므로 두 항목을 같은 병합에서 함께 처리하는 편이 안전하다.

## 4. 기확정 표기 준수 확인 (변경 제안 없음)

- `parameter`→매개변수 / `argument`→인자 구분을 지킨다. 166·273·431·458·513줄이 정의 쪽에
  "매개변수", 호출 쪽에 "인자"를 쓰고 있고 뒤바뀐 곳이 없다.
- `expression`→식(복사-수정 레코드 식, 계산 식), `side effect`→부수 효과,
  `class type`→클래스 타입, `discriminated union`→판별 유니온, `type abbreviation`→타입 약어,
  `auto-generalization`→자동 일반화, `value restriction`→값 제한, `computation expression`→계산 식,
  `validation`→검증, `record`→레코드, `mutable`→가변 모두 확정 표기대로다.
- `type`→"타입"을 지키고 "형식"은 컴파일러 메시지 인용 안에서만 쓴다(166줄의 `error FS0001` 언급은
  코드만 인용하고 메시지 본문을 옮기지 않았다).
- 챕터 표기는 전부 `N챕터` 다. `N장` 없음.
- 굵은 글씨 없음. `check-note.sh` 통과.
