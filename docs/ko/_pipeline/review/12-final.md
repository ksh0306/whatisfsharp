# 12챕터 최종 검수 지시서 — 용어·문법·문체

대상: `docs/ko/12-computation-expressions.md` (627줄, 실행 단위 6개)
기준: `docs/ko/GLOSSARY.md` (334행), `docs/ko/_pipeline/STYLE.md`
함께 검수한 것: `docs/ko/_pipeline/review/12-expert.md` (교체 문장 11건)

줄 번호는 참고용이다. STYLE.md "검수 지시서를 적용하는 방법" 대로 유일한 문자열로 특정하고 치환하라.
아래 항목은 서로 겹치지 않으므로 순서는 자유다. 단 전문가 지시서와 같은 자리를 건드리는 항목은
"선행 검수 지시서의 문제" 절에 모아 두었으니 그쪽 수정형을 최종으로 삼아라.

## 확인 완료 (고칠 것 없음)

- 대조 표의 실행 단위 `id` 6개가 본문에 쓰인 `id` 와 정확히 일치한다
  (`12-option-manual`·`12-option-builder`·`12-result-ce`·`12-async`·`12-asyncresult`·`12-do-bang`).
  절 제목·페이지 표기도 표와 한 글자씩 맞고, 모든 절에 `(원서 p.NN)` 이 있다. `정리 — 이 노트의 요약`
  절을 표에 넣지 않은 것도 11·08챕터 관례와 같다.
- `](examples/...)`·`docs/ko/examples` 형태의 폐기된 링크가 없다. `.fsx` 파일 참조도 없다.
- 코드 블록이 절 끝에 몰려 있지 않고 설명 사이사이에 놓였다. `id` 없는 블록 4개(37·140·274·525줄)는
  시그니처·컴파일 오류 예시라 정상이다.
- 용어집이 이 챕터 때문에 바뀐 3건이 노트 서술과 맞는다.
  `do!` 의 두 경우가 543줄과 606줄에서 정확히 갈려 있다 — `async`·손으로 만든 빌더는 `error FS0001`,
  `FsToolkit.ErrorHandling` 의 `result` 는 `Source` 오버로드 때문에 `error FS0041`.
  529-531·537줄 주석도 이 갈림과 어긋나지 않는다. 빌더 멤버 이름(`Bind`·`Return`·`ReturnFrom`·
  `Zero`·`Combine`·`Source`·`MergeSources`)은 전부 번역하지 않고 백틱 원어이며 "작성기" 표기가 없다.
  `%A` 의 폭 지정 문제도 72줄 주석과 `show` 의 `sprintf "%A"` 우회로 그대로 반영돼 있다.
- 08챕터 664줄 예고(병합 보고서 4.6)와 어긋나지 않는다. 593줄이 "이 챕터에서 만든 `Bind` 가 아니라
  `MergeSources` 멤버를 부른다" 로 적어 12챕터가 `MergeSources` 를 만든다고 읽힐 자리가 없다.
  08챕터 쪽 문장만 좁히면 되고 12챕터는 손댈 것이 없다.
- 금지 패턴 8종(`표현식`·`부작용`·`일급 값`·`컴파일 에러`·`씨드`, have 직역, 번역체, 1인칭, `N장`,
  굵은 글씨)이 본문에 없다. 아래에 제시한 수정 문장 전부를 `check-note.sh` 검사식으로 미리 돌려
  위반이 없음을 확인했다.

## 선행 검수 지시서의 문제

전문가안 11건 가운데 6건에 수정형이 필요하다. 나머지는 그대로 적용해도 표기·문법에 걸리는 것이 없다.

- [기술 오류 :460] 전문가안: "반환 타입 주석은 없어도 컴파일된다. 네 줄에 나오는 `UnknownRider`·
  `WrongPin`·`NotInGoodStanding`·`IssueFailed` 가 모두 …"
  → 수정형: "반환 타입 주석은 없어도 컴파일된다. 계산 식 네 줄에 나오는 `UnknownRider`·`WrongPin`·
  `NotInGoodStanding`·`IssueFailed` 가 모두 `PassError` 의 케이스라 실패 타입이 그 자리에서 정해지고,
  주석을 떼도 `Async<Result<DayPass,PassError>>` 로 유추된다(실측 확인). 주석은 네 단계를 겹친 반환
  타입을 한눈에 보이게 하려고 원서가 적어 둔 것이다."
  ("네 줄" 이 무엇의 네 줄인지 문장 안에 없다. 바로 위 442-450줄 계산 식의 네 줄이므로 한정어를
  붙인다. 나머지 문면은 용어집 표기(케이스·시그니처·실측 확인)를 따르고 있어 그대로 둔다.)

- [기술 오류 :287] 전문가안: "값 제한은 매개변수 없는 `let` 에만 걸리고, 매개변수가 있으면 정해지지
  않은 타입이 자동 일반화된다."
  → 수정형: "값 제한에 걸릴 수 있는 것은 매개변수 없는 `let` 뿐이고, 매개변수가 있으면 정해지지 않은
  타입이 자동 일반화된다."
  (전문가안의 "…에만 걸리고" 는 필요조건을 적은 것인데 "매개변수가 없으면 걸린다" 는 충분조건으로
  읽힐 여지가 있다. `GLOSSARY.md:356` 과 05챕터 28줄은 매개변수 없는 `let` 이라도 `[]` 처럼 값 자체는
  자동 일반화되어 값 제한에 걸리지 않는다고 적어 두었다. 05챕터가 이 개념을 거꾸로 적었던 자리이므로
  조건 방향이 한 번 더 뒤집히지 않게 못 박는다. 나머지 세 문장 — `let wrap` 실측, `settleCe` 는
  자동 일반화까지 갈 일도 없다는 대목 — 은 그대로 두면 된다.
  같은 문단 뒤쪽의 "참고로 `result { ... }` 를 패키지 없이 적으면 …" 문장은 손대지 않는다.)

## 용어집 쪽으로 넘길 것 (노트는 손대지 마라)

- `GLOSSARY.md:116` (`do!` 행)이 스스로 갈린다. 서술문은 "효과가 감싼 `unit`(`Result<unit,'e>`·
  `Async<unit>`)을 받아 …" 로 쓰고, 같은 행 끝의 지시문은 ""`unit` 을 감싼 효과" 로 쓴다" 다.
  노트 490줄과 606줄은 서술문 쪽 문면을 글자까지 그대로 따르고 있다(`효과가 감싼
  `unit`(`Result<unit,'e>`·`Async<unit>`)`). 두 문면 중 어느 쪽이 등재 표기인지 정해지기 전에는
  노트를 고치지 마라 — 지금 상태가 용어집 본문과 일치한다. 용어집 편집 권한은 F# 전문가에게 있으므로
  `do!` 행의 서술문과 지시문을 한 문면으로 맞춰 달라고 넘긴다.
