# Essential F# 한국어 학습 노트 — 공용 작업 지침

## 이 문서의 성격 (중요)
원서 `docs/essential-fsharp.pdf`(© 2021-2023 Ian Russell, 상업 출판물)를 **번역하는 것이 아니다**.
원서를 옆에 두고 읽는 독자를 위한 **한국어 학습 노트**를 만든다.

지켜야 할 선:
- 각 절은 **요약**한다. 원문 문장을 옮기거나, 옮긴 뒤 단어만 바꾸는 방식은 금지.
- 개념 설명은 **자신의 언어로** 새로 쓴다.
- 코드 예제는 같은 개념을 보여주는 **새로 작성한 실행 가능한 F# 코드**를 쓴다.
  원서 코드를 그대로 옮기지 않는다. 변수명·도메인·구성을 달리 잡되 개념은 동일하게 전달한다.
- 원문 인용은 꼭 필요할 때 한 문장 이내로, 인용 표시와 페이지를 함께 단다.
- 각 절 제목 옆에 원서 인쇄 페이지를 `(원서 p.33)` 형태로 달아 대조가 가능하게 한다.

## 출력 위치
- 노트: `docs/ko/<NN>-<slug>.md` — **소스코드까지 이 파일 하나에 들어간다.**
- 용어집: `docs/ko/GLOSSARY.md` (F# 전문가만 편집)

별도 `.fsx` 파일을 만들지 않는다. 코드는 노트 본문의 펜스 블록으로 넣고,
검증할 때만 `docs/ko/_pipeline/verify-examples.sh` 가 시스템 임시 경로로 추출해 실행한다.
노트가 유일한 원본이다.

## 코드 블록 규칙

### 실행 단위에는 id 를 붙인다
```` ```fsharp id=02-currying ```` 형태로 정보 문자열에 `id` 를 적는다.
- **같은 `id` 를 가진 블록들은 문서에 나온 순서대로 이어 붙여 하나의 스크립트로 실행된다.**
  따라서 앞 블록에서 정의한 것을 뒤 블록에서 그대로 쓸 수 있다. 절 안에서 코드를 여러 덩어리로
  쪼개 설명 사이사이에 넣어라. 한 블록에 몰아넣지 마라.
- `id` 는 `<NN>-<주제>` 로 짓는다. 챕터당 3~6개 실행 단위가 적당하다.
- 한 절이 여러 실행 단위에 걸치거나, 여러 절이 한 실행 단위를 공유해도 된다.
  개념 단위로 묶는 것이 기준이다.

### id 없는 블록은 실행되지 않는다
```` ```fsharp ```` 로만 적은 블록은 검증에서 제외된다. 다음 용도로만 쓴다.
- 시그니처만 보여주는 조각: `let add : int -> int -> int`
- 컴파일 오류를 일으키는 예: `|> 3` 은 오류다
- 문법 형태만 보여주는 불완전한 조각

컴파일되는 완전한 코드라면 반드시 `id` 를 붙여 검증 대상에 넣어라.

### 코드 내용
- 각 실행 단위의 첫 블록 위에 그 단위가 무엇을 보여주는지 한 줄로 적는다.
- 주석은 한국어.
- 결과를 `printfn` 으로 눈에 보이게 출력하고, 기대 출력을 주석으로 적는다.
- **시그니처 주석은 반드시 FSI 로 실측한 값을 적는다.** 자동 일반화 때문에 손으로 예상한 것과 자주 다르다.
  제약이 있으면 함께 적는다: `'a -> 'a -> bool  (when 'a : comparison)`

## 문체
- 평서형 종결 `-다`. "~해요/~합니다" 섞지 않는다.
- F# 코드 식별자·연산자는 백틱: `List.map`, `|>`, `Option`.
- 용어는 `한국어(영어)` 첫 등장 1회, 이후 한국어만. 용어집을 따른다.
- 원서 저자의 1인칭("we will...")을 그대로 옮기지 않는다. 설명체로 쓴다.

## 금지 패턴 (2장 검수에서 반복 지적된 것 — 집필 단계에서 미리 피할 것)

1. **영어 `have` 직역** — "~을 가진다 / 가져야 한다 / 가지므로".
   → "레코드는 구조적 동등성을 가진다" ✗ / "레코드는 구조적 동등성이 있다" ○
2. **주술 불일치** — 주어와 서술어가 어긋난 문장. 특히 긴 문장과 열거문에서 자주 난다.
   → "이 챕터는 ~ 넘어간다" ✗ / "다음 챕터에서는 ~ 살펴본다" ○
3. **`매개변수`와 `인자` 혼용** — `parameter`=매개변수(정의 쪽), `argument`=인자(호출 쪽). 정의를 설명하며 "인자"를 쓰지 말 것.
4. **원서 1인칭** — "우리는 ~할 것이다". 설명체로 쓴다.
5. **번역체** — "~에 대해", "~을 통해", "~되어진", 불필요한 피동.
6. **`N장` / `N챕터` 혼용** — `N챕터`로 통일.
7. **굵은 글씨** — 노트 본문에 `**...**` 를 쓰지 않는다.
8. **금지 표기** — `표현식`(→식), `부작용`(→부수 효과), `일급 값`(→일급 시민), `컴파일 에러`(→컴파일 오류), `씨드`(→시드).

## 완료 검증 (필수, 생략 금지)
```bash
docs/ko/_pipeline/verify-examples.sh docs/ko/<NN>-<slug>.md
docs/ko/_pipeline/check-note.sh      docs/ko/<NN>-<slug>.md
```
실행 단위 전부 PASS, 금지 패턴 검사 OK 여야 완료다.
`check-note.sh` 가 게이트의 단일 출처다. **직접 grep 을 짜지 마라** — 검사식이 갈라지면 게이트를 못 믿는다.
빠진 검사가 있으면 스크립트를 고칠 일이므로 보고하라.

주석에 적은 기대 출력이 실제 출력과 일치하는지도 확인한다.
`printfn` 라벨 폭을 바꿨으면 열 정렬이 깨지지 않았는지 본다.

컴파일러·FSI 메시지 인용은 원문 표기를 유지한다. `check-note.sh` 의 문체 검사는
백틱 인라인 코드를 제외하므로 인용을 위반으로 잡지 않는다.

## 검수 지시서를 적용하는 방법 (줄 번호를 좌표로 쓰지 마라)

검수 지시서의 줄 번호는 **참고용이다.** 두 가지 이유로 어긋난다.
- 검수자가 잘못 적는 경우가 있다(배치 B 에서 두 챕터에 걸쳐 4건 발생했다).
- 앞 항목을 적용하면 뒤 항목의 줄 번호가 밀린다.

그러므로 다음 절차로 적용하라.
1. 편집 전에 대상 구간을 `cat -n` 이나 `sed -n` 으로 출력해 **내용을 눈으로 확인**한다.
2. 줄 번호가 아니라 **유일한 문자열**로 대상을 특정한다.
3. 치환 전에 그 문자열의 출현 횟수가 1인지 단정한다(`grep -c` 로 확인). 2 이상이면 문맥을 더 넣어 좁힌다.
4. 지시서의 줄 번호와 실제 내용이 어긋나면 **내용을 따르고 그 사실을 보고하라.**

이렇게 하면 지시서 번호가 틀려도 다른 절에 글이 들어갈 수 없다.

## 지시서가 서로 충돌하거나 실측과 다를 때
- 전문가 지시와 최종 검수 지시가 같은 곳을 건드리면 **최종 검수가 우선**이다.
- 지시서 내용이 FSI 실측과 다르면 **실측을 따르고 보고하라.** 검수자도 틀릴 수 있다.
- 지시를 적용했더니 문서 다른 곳의 서술이 낡게 되면, 지시서에 없어도 함께 고치고 보고하라.
